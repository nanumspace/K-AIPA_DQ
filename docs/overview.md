# 개요: 배경, 설계 원칙, 계획

> **범위.** [K-AIPA](https://k-aipa.org/overview)는 K-AI 신약개발의 전임상·임상 모델개발 사업입니다. 이 저장소의 K-AIPA DQ 는 그중 **여섯 질환 코호트 임상 테이블의 품질검증**만 다룹니다. 전임상·오믹스 데이터와 AI 모델의 검증, 임상적 적절성의 판정이나 인증은 범위 밖이며, K-AIPA 의 공식 승인·후원을 받았다는 주장도 아닙니다.

## 배경

여섯 질환 코호트(폐암, 유방암, 대장암, 대사이상지방간, 당뇨병, 림프종)는 여러 병원이 같은 데이터 사전을 따라 구축합니다. 병원마다 구축한 데이터가 사전에 맞는지, 테이블 사이의 논리가 맞는지 확인하는 품질검증 프로그램이 필요합니다. 그런데 검증 프로그램은 병원 데이터가 만들어지기 **전에** 준비되어야 하므로, 실제 데이터를 한 번도 보지 않은 상태에서 개발해야 합니다.

검증 기준은 의뢰사의 **「질환별 데이터 테이블」 매뉴얼 2026-11-16**(`raw/매뉴얼_질환별 데이터 테이블_20261116.xlsx`) 하나입니다.

## 코호트 DB 구조

여섯 코호트는 모두 OMOP-CDM 핵심 8개 테이블(PERSON, VISIT_OCCURRENCE, PROCEDURE_OCCURRENCE, DRUG_EXPOSURE, CONDITION_OCCURRENCE, MEASUREMENT, OBSERVATION, NOTE)을 공유하고, 여기에 질환 본표와 이상사례(ADVERSE_EVENT) 테이블이 붙습니다. 폐암·유방암·대장암·림프종에는 항암요법(SACT) 테이블이 추가됩니다. 병원이 표를 직접 채워 넣으며, 별도의 서식을 채워 변환하는 단계는 없습니다.

| 코호트 | 질환 본표 (필드 수) | 이상사례 | 항암요법 (SACT) | 표 수 |
|---|---|---|---|---|
| 폐암 | LUNG_CANCER (8) | O | O | 11 |
| 유방암 | BREAST_CANCER (10) | O | O | 11 |
| 대장암 | COLORECTAL_CANCER (11) | O | O | 11 |
| 대사이상지방간 | MASLD (8) | O | X | 10 |
| 당뇨병 | DIABETES (5) | O | X | 10 |
| 림프종 | LYMPHOMA (15) | O | O | 11 |

전체 명세는 18개 테이블, 178개 필드입니다. 매뉴얼은 16개 테이블, 157개 필드이고(공통 8표 76필드, 질환 본표 6표 57필드, SACT 13필드, ADVERSE_EVENT 11필드), 여기에 매뉴얼 보완으로 선택 컬럼 6개(`condition_`·`procedure_`·`drug_` 의 `*_source_value`, `*_source_concept_id`)와 선택 테이블 2개(CONCEPT·VOCABULARY, 필드 15개)가 더해집니다. 선택 컬럼(원천 코드)과 선택 테이블은 없어도 오류가 아니고, 내면 표준 용어(OHDSI v20260829)와 대조합니다([vocabulary.md](vocabulary.md)). 코호트별 테이블 구성은 `spec/cohort_profiles.yaml`에 고정되어 있습니다.

## 설계 원칙

병원 데이터 없이 검증 프로그램을 개발하려면 가상데이터가 필요합니다. 규칙과 가상데이터는 다음 세 원칙을 따릅니다.

1. **규칙은 데이터가 아니라 사전에서 나옵니다.** 사전이 모호한 부분을 생성기가 임의로 메우면, 그 데이터로 만든 규칙은 사전이 아니라 생성기의 가정을 검증하게 됩니다. 그래서 매뉴얼을 먼저 기계 판독 명세(`spec/kai_cdm_spec.yaml`)로 고정하고, 규칙과 가상데이터를 같은 명세에서 만듭니다. 매뉴얼에 없는 표·열은 만들지 않고, 매뉴얼이 말하지 않는 값 제약은 `spec/constraints.yaml`에 따로 적어 **경고**로만 다룹니다.
2. **검증 프로그램은 오류가 들어 있는 데이터로 시험합니다.** 규칙을 만족하는 clean 데이터만으로는 오탐 여부만 확인할 수 있습니다. 오류를 알고 주입한 dirty 데이터와, 오류마다 잡아야 할 규칙 id를 기록한 정답 manifest가 있어야 주입 오류의 검출 여부를 잴 수 있습니다.
3. **분포 검사에는 충분한 환자 수가 필요합니다.** 성비, 나이 분포, 검사값 분포 같은 타당성 규칙은 수십 명 이상이 있어야 의미가 있습니다. 그래서 질환당 100명을 시드 기반으로 생성하고, 필요하면 같은 시나리오로 늘립니다.

가장 큰 위험은 검증 프로그램이 아니라 **사전 자체의 모호함**입니다. 병원마다 사전을 다르게 해석하면 검증 프로그램은 데이터 품질과 무관한 이유로 실패합니다. 그래서 매뉴얼의 해석을 명시적으로 고정하고(예: NOTE의 필수 열, SMILES의 위치, `cell_of_origin`의 `NA`, 폐암 병기, `diag_rgst_ymd`의 뜻) [명세와 규칙 카탈로그](spec-and-rules.md)에 적습니다.

LLM의 역할은 데이터를 직접 생성하는 것이 아니라 **환자 여정 시나리오와 판독문 템플릿을 작성**하는 것입니다. 실제 행 생성은 시드 기반 프로그램이 하므로 재현 가능하고 규모를 늘릴 수 있습니다.

## 5단계 계획

```
                    ┌─ 단계 1 규칙 카탈로그 ─┐
데이터 사전 → 단계 0 명세 ┤                        ├→ 단계 3 검증 프로그램 → 단계 4 병원 파일럿
                    └─ 단계 2 가상데이터 3종 ─┘         ↑ 집계 통계로 임계값 보정 ┘
```

| 단계 | 내용 | 산출물 | 상태 (2026-11-16) |
|---|---|---|---|
| 0 | 매뉴얼 해석과 기계 판독 명세 | `spec/*.yaml` | 완료 |
| 1 | 검증 규칙 카탈로그 | `rules/*.yaml` | 완료 |
| 2 | 가상데이터 세 벌 (clean, dirty + manifest, good) | `synth/output/` | 완료 |
| 3 | 검증 프로그램 (Python 참조 → TypeScript 엔진 → 데스크톱 앱) | `dq/`, `dq-ts/`, `app/` | 완료 |
| 4 | 1개 병원 파일럿. 병원이 직접 실행하고 집계 통계만 회수해 임계값 보정 | `pilot/` | 착수 전 |

"본 적 없는 데이터" 문제는 단계 4에서만 실질적으로 해소됩니다. 단계 0~3의 결과는 프로그램이 규칙을 정확히 구현했다는 증거이지 병원 데이터 품질에 대한 예측이 아닙니다.

## 검증 프로그램의 세 층

| 층 | 위치 | 역할 |
|---|---|---|
| Python 참조 구현 | `dq/` | 규칙 의미의 기준. 가상데이터 생성·오류 주입과 함께 개발 도구로 유지 |
| TypeScript 엔진 | `dq-ts/` | 앱에 들어가는 엔진. Python과 동등성이 회귀 시험으로 고정됨. 규칙 설정(켜고 끄기, 조정, 사용자 규칙)은 이 층에만 있음 |
| 데스크톱 앱 | `app/` | 병원 담당자가 쓰는 프로그램. 입력 처리, 실행, 이력, 출력물, 규칙 설정 |

명세(`spec/`)와 규칙(`rules/`)은 세 층이 같은 YAML을 읽으므로, 표준 규칙을 고치면 한 곳만 바꾸면 됩니다.
