# 파일럿 키트 (K-AIPA DQ)

실제 병원 데이터로 **K-AIPA DQ**(K-AIPA 임상 데이터 품질검증) 1.0.0 을 처음 돌리는 파일럿을 위한 묶음입니다. 파일럿은 의뢰사 매뉴얼 2026-11-16 기준(표 16개 · 필드 157개 · 규칙 390개, 병원이 표를 직접 채움)으로 진행합니다. 지금까지 규칙은 가상데이터로만 검증했습니다. 파일럿이 답해야 할 질문은 하나입니다 — **실제 데이터에서 규칙이 우선 표시하는 문제는 무엇인가.** 오탐이 어디서 나는지, 명세가 현장과 어디서 어긋나는지, 입력 준비의 어느 단계가 막히는지.

## 파일럿의 범위

[K-AIPA](https://k-aipa.org/overview) 사업은 K-AI 신약개발의 전임상·임상 모델개발을 다룹니다. 이 파일럿이 다루는 것은 그중 **여섯 질환(폐암·유방암·대장암·대사이상지방간·당뇨병·림프종) 임상 코호트 테이블이 매뉴얼 명세에 맞는지**뿐입니다. 전임상·오믹스·AI 모델 데이터의 검증, 임상적 적절성의 판정, 임상 데이터 인증, 제출 승인은 이 프로그램과 파일럿의 범위 밖입니다. 이 키트는 K-AIPA 의 공식 승인이나 후원, 로고 사용 허락을 받았다는 뜻이 아닙니다.

| 파일 | 용도 |
|---|---|
| [`README.md`](README.md) (이 문서) | 참여 기관이 할 일, 보내는 것과 보내지 않는 것, 일정 |
| [`feedback.md`](feedback.md) | 기관이 채워 보내는 피드백 양식 (환자 정보 없이 쓰는 요령 포함) |
| [`feedback_rules.csv`](feedback_rules.csv) | 규칙 단위 이의를 표로 적을 때 쓰는 헤더 |
| [`central-runbook.md`](central-runbook.md) | 중앙(파일럿 운영 측)의 접수·집계·판정·회신 운영 절차 |
| [`adjudication.csv`](adjudication.csv) | 중앙이 규칙 이의를 판정·추적할 때 쓰는 운영 양식 헤더 (앱 기능이 아님) |
| [`aggregate.py`](aggregate.py) | 중앙이 여러 기관의 `submission.json` 을 모아 규칙별로 집계하는 도구 |

## 참여 기관이 할 일

1. **설치.** [Releases](https://github.com/nanumspace/K-AIPA_DQ/releases)에서 설치 파일(`K-AIPA-DQ-<버전>-…`)을 받아 설치합니다. → [설명서 1장](../manual/01-install.md)
2. **동작 확인.** 같은 페이지의 견본 데이터 zip 하나(예: `SampleData-<버전>-LUNG_CANCER-dirty.zip`)를 넣어 README.txt 의 참조 결과와 위반 건수가 같은지 봅니다. 다르면 설치 문제이니 먼저 알려 주세요.
3. **코호트 테이블 준비.** 코호트의 질환 본표와 공통 표(PERSON, VISIT_OCCURRENCE, PROCEDURE_OCCURRENCE, DRUG_EXPOSURE, CONDITION_OCCURRENCE, MEASUREMENT, OBSERVATION, NOTE, ADVERSE_EVENT, SACT; MASLD·당뇨병은 SACT 없음)를 CSV 로 만듭니다. 컬럼은 **입력 양식 내려받기 → 엑셀 양식·컬럼 명세서**를 따릅니다. 사례가 없는 표도 헤더만 있는 파일로 둡니다. → [설명서 2장](../manual/02-input.md)
4. **직접 채우는 항목.** 서식을 따로 채워 바꾸는 단계는 없습니다. EHR 에 없는 항목(병기, 병리, 바이오마커, SACT 연결 등)은 해당 표의 컬럼에 직접 채웁니다. 파일럿에서는 **모든 컬럼을 채우지 않아도 됩니다** — 준비된 것부터.
5. **사전 점검.** 앱의 **검증 실행** 화면에 파일을 넣고 대응표와 사전 점검의 오류(PERSON·질환 본표 누락 등)를 해결합니다. → [설명서 3장](../manual/03-run.md)
6. **검증 실행.** 표 폴더(또는 엑셀 한 파일)를 넣고 실행합니다. 검증 실행일은 **데이터를 뽑은 날**로 맞춥니다. 실행 이름에는 환자를 알아볼 수 있는 말을 넣지 않습니다.
7. **결과 보기.** 위반이 많이 나오는 것이 정상입니다. 형식 문제(컬럼 구성·타입)를 먼저 고치고 한 번 더 돌린 뒤, 남는 것을 봅니다. 결과를 읽을 때는 **건너뜀·오류·꺼짐 규칙은 통과가 아니라 검사하지 않은 것**이며, 위반율은 오류가 있는 환자의 비율이 아님을 기억하세요. → [설명서 4장](../manual/04-output.md)
8. **보내기.** 아래 "보내는 것"을 보내 주세요.

처음 한 번은 3~6 단계에 걸린 시간을 적어 주시면 다음 기관의 안내에 씁니다.

### 규칙을 조정하고 싶다면

오탐이 분명한 규칙은 앱에서 끄거나 범위를 조정한 채로 실행해도 됩니다([설명서 6장](../manual/06-rules.md)). 다만 **첫 실행은 규칙을 조정하지 않은 표준 상태**로 해 주세요. 그래야 중앙이 기관 간 비교를 할 수 있습니다. 조정한 실행의 `submission.json` 에는 그 사실(`rule_set`)이 실려 있고, 중앙은 표준 규칙의 결과와 따로 집계합니다. 관리자 모드(SQL 수정)는 파일럿 기관에는 권하지 않습니다.

## 보내는 것

| 무엇 | 어디서 | 왜 |
|---|---|---|
| `submission.json` | 실행 폴더 (결과 화면의 **실행 폴더 열기**) 또는 **다른 이름으로 저장** | 규칙별 통과·실패·위반 건수, 표별 행 수, 입력 정규화 건수, 규칙 설정 요약. **환자 단위 정보를 넣지 않도록 만든 파일** |
| `feedback.md` (채운 것) | 이 폴더의 양식 | 오탐이라고 보는 규칙, 명세가 현장과 다른 곳, 값 집합에 없는 코드, 준비하며 막힌 곳 |
| `feedback_rules.csv` (선택) | 이 폴더의 양식 | 규칙 단위 이의가 많을 때 표로 |

**보내기 전에 `submission.json` 을 텍스트 편집기로 열어 확인하세요.** 실행 이름(`label`)과 `rule_set` 의 내용에 환자·병원 내부 식별 정보가 없는지 봅니다. 파일은 고치지 말고 그대로 보냅니다. 전달 방법(채널)과 받는 곳은 파일럿 운영 측이 별도로 안내합니다. 이 문서는 정하지 않습니다.

두 번 돌렸다면(형식 문제 고치기 전·후) `submission.json` 두 개를 모두 보내 주세요. 두 파일은 `run_id`(실행 ID)로 구분되며, 파일 이름은 두 파일이 서로 다르게 남도록 해 주세요. 앱이 **다른 이름으로 저장**할 때 주는 기본 이름 `<실행 ID>_submission.json` 을 그대로 쓰면 구분됩니다. **어느 쪽이 첫 표준 실행이고 어느 쪽이 수정 후 실행인지** 피드백 양식에 적어 주세요. 이 구분이 없으면 중앙이 늦은 실행으로 첫 실행을 덮어 읽게 됩니다([중앙 운영 절차](central-runbook.md)).

## 보내지 않는 것

- `findings.csv`, **오류 현황 조회**에서 내보낸 CSV — 환자 ID 와 값이 들어 있습니다.
- 실행 폴더의 `input/` — 정규화된 입력 데이터 사본입니다.
- 코호트 테이블 파일 — 데이터 자체입니다.
- **결과 폴더로 내보내기**로 만든 폴더째 — 위 `findings.csv` 가 들어 있습니다.
- 위반 행의 값, 환자 ID·생년월일·진료일 등 실제 환자 값이 보이는 화면 캡처나 메모.

`report.md`, `rule_results.csv`, `summary.json` 은 환자 단위 값을 담지 않게 만들었지만, 보내기 전에 기관이 확인해야 하고 중앙이 요청했을 때만 보냅니다. `submission.json` 의 `label`(실행 이름)은 그대로 실립니다.

### 피드백은 환자 정보 없이 씁니다 (필수)

피드백(`feedback.md`, `feedback_rules.csv`, 메일·메신저 등 모든 문의)에는 **실제 환자의 값을 적지 않습니다.** 환자 ID, 이름, 생년월일, 진료·검사 날짜의 실제 값, 검사 수치, 의무기록 문구가 보이는 화면 캡처를 포함합니다. "규칙 SEM-COM-006 이 외래 처방에서 계속 걸린다, 우리는 매일 투여라도 days_supply 를 비워 둔다" 정도의 규칙 id 와 상황 설명이면 충분합니다. 작은 표에서 한 사람을 알아볼 수 있는 조합(희귀한 병기와 날짜 등)도 쓰지 않습니다. 작성 요령과 예시는 [`feedback.md`](feedback.md)에 있습니다.

## 중앙이 돌려주는 것

- 기관별 결과 요약과, 여러 기관에서 함께 우는 규칙 목록(`aggregate.py` 산출물).
- 이의에 대한 중앙의 판정(수용·기각 등)과 근거, 받아들여진 규칙의 수정 내역과 다음 판 앱. 판정 절차는 [중앙 운영 절차](central-runbook.md)에 있습니다.
- 값 집합에 보탠 코드.

규칙·명세·값 집합은 앱 안에 들어 있으므로 수정은 **새 앱 버전을 배포**해야 반영됩니다. 앱이 스스로 업데이트하는 기능은 없어서, 기관이 새 설치 파일을 받아 설치합니다. 어떤 일정으로 배포할지는 이 문서가 정하지 않습니다.

## 중앙 집계 (`aggregate.py`)

자세한 절차와 주의는 [중앙 운영 절차](central-runbook.md)에 있습니다. 요약만 적습니다.

```bash
python pilot/aggregate.py <submission.json 파일 또는 폴더> ... [--out pilot/out] [--name "<파일 경로>=<기관>"]
```

- **집계 전에 제출분을 점검합니다.** 도구는 파일의 `schema` 접두사(`kai-dq-submission/`)만 확인해 읽을지 말지 정합니다. 앱 버전, `rule_set`, `standard_hash` 가 서로 다른 제출분을 **자동으로 갈라 놓지 않으며**, 해시가 둘 이상이면 `summary.md` 에 경고 문장만 적습니다. `rule_set` 이 없는 제출분이나 `origin` 이 없는 규칙은 코드가 표준으로 간주하지만, 운영상으로는 **확인되지 않은 것**입니다.
- **기관·코호트마다 가장 늦은 실행 하나**(`generated_at`)만 씁니다. 첫 실행(표준)과 수정 후 실행, 표준 실행과 규칙을 조정한 실행은 같은 입력 묶음에 섞지 않고 **입력 묶음을 나눠 따로 집계**합니다.
- **폴더를 넘기면 이름이 정확히 `submission.json` 인 파일만 찾습니다.** `<실행 ID>_submission.json` 처럼 바뀐 이름은 폴더 검색에 잡히지 않으므로 파일 경로를 직접 넘깁니다. 기관 이름은 파일이 든 폴더 이름이므로 `--name` 으로 분명히 지정합니다.
- 규칙이 여러 기관에서 우는지 볼 때의 분모는 기관이 아니라 **기관×코호트 조합**입니다.

산출물은 다음과 같습니다.

| 파일 | 내용 |
|---|---|
| `sites.csv` | 기관·코호트마다 규칙·위반·행 수, 정규화 건수, **규칙 설정 상태**(표준 / 규칙 조정 / 관리자 수정)와 꺼진·바꾼·사용자·관리자 규칙 수 |
| `rules_by_site.csv`, `rules_summary.csv` | 규칙 × 기관 표와 규칙별 요약. **출처가 표준이고 꺼지지 않은 규칙의 결과만** 들어감 |
| `nonstandard_rules.csv` | 끈 규칙, 조정한 규칙, 사용자(`USR-###`)·관리자(`ADM-###`) 규칙의 기관별 결과. 기관 간 비교에 섞지 않음 |
| `summary.md` | 모든 기관·코호트에서 우는 규칙(규칙·명세를 의심), 한 곳에서만 우는 규칙(그 기관의 내보내기를 의심), 입력 정규화, 규칙 설정이 표준이 아닌 실행, 해시 경고 |

## 일정 (안)

| 주 | 할 일 |
|---|---|
| 1 | 설치, 견본 데이터로 동작 확인, 코호트 테이블 준비 시작 |
| 2–3 | 테이블 완성(EHR 에 없는 항목 직접 채우기), 첫 실행 |
| 4 | 형식 문제 고친 뒤 두 번째 실행, `submission.json` 과 피드백 송부 |
| 5 | 중앙 집계와 규칙 수정, 결과 회신 |

## 파일럿에서 알고 싶은 것 (중앙의 체크리스트)

- [ ] 설치가 병원 PC(망 분리·보안 정책)에서 되는가
- [ ] 테이블 준비에 며칠 걸리는가, 어느 표·컬럼이 어려운가
- [ ] 내보내기 흔적(인코딩·대문자·NULL·`.0`·구분자)이 실제로 어떤 모양으로 오는가 — `submission.json` 의 `normalization`
- [ ] 코드표가 충분한가, 어느 값 집합이 모자라는가 (`sact_id` 연결, OMOP 대표 코드 경고, `cell_of_origin` 의 `NA` 포함)
- [ ] 규칙 가운데 **모든 기관·코호트에서 우는 것** — 규칙이나 명세의 문제일 가능성이 크다
- [ ] 규칙 가운데 **한 곳에서만 우는 것** — 그 기관의 내보내기나 관행일 가능성이 크다
- [ ] 기관이 **끄거나 조정한 규칙**과 그 이유 — 표준 규칙을 고칠 근거
- [ ] **건너뜀·오류** 규칙이 많은 기관 — 표 누락이나 실행 오류로 검사되지 않은 영역
- [ ] 실행 시간과 메모리 (2,000명 규모까지는 확인했다)
- [ ] 보고서가 담당자에게 읽히는가, 조치 안내가 도움이 되는가
