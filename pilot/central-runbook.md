# 중앙 운영 절차 (파일럿)

파일럿을 운영하는 중앙 측이 여러 기관의 `submission.json` 을 **받고, 점검하고, 집계하고, 이의를 판정하고, 회신하는** 절차입니다. 기관 쪽 안내는 [README](README.md)와 [사용자 설명서](../manual/README.md)에 있습니다.

## 먼저 알아 둘 것

- **범위.** 이 절차가 다루는 것은 여섯 질환(폐암·유방암·대장암·대사이상지방간·당뇨병·림프종) 임상 코호트 테이블의 검증 결과뿐입니다. 전임상·오믹스·AI 모델 데이터는 다루지 않으며, K-AIPA 의 공식 절차가 아닙니다.
- **`submission.json` 은 인증된 파일이 아닙니다.** 서명이 없는 일반 텍스트이고, 안의 해시(`standard_hash`, `effective_hash`)는 규칙 묶음의 지문일 뿐 파일의 진본·무결성을 증명하지 않습니다. 파일이 기관이 만든 그대로인지는 도구로 알 수 없으므로 접수 기록과 기관과의 확인으로 다룹니다.
- **등급은 공식 판정이 아닙니다.** 앱의 우수·양호·주의·위험은 내부 점검용 구간이며, 공식 접수·합격 기준이 아닙니다. 중앙이 기관의 제출을 "합격·불합격"으로 처리하려면 그 기준은 파일럿 운영 정책으로 따로 정해야 합니다(이 저장소는 정하지 않음).
- **이 문서가 정하지 않는 것**(전달 채널, 보관 기간과 폐기 방법, 판정·승인 권한자, 연락 창구)은 아래 "시작 전에 정할 것"에서 **파일럿 운영 정책으로 정하는 항목**으로 표시합니다. 이 저장소에는 담당자나 연락처가 없습니다.
- **저장소에 넣지 않습니다.** 이 저장소는 공개입니다. 기관에서 받은 파일(`submission.json`, 피드백)과 집계 산출물(`pilot/out`)은 저장소 밖의 접근 통제된 위치에 두고 커밋하지 않습니다.

## 역할

역할 이름은 이 문서에서 업무를 나누려고 붙인 것입니다. 누가 어느 역할을 맡는지, 한 사람이 여럿을 겸하는지는 **파일럿 운영 정책으로 정합니다.**

| 역할 | 하는 일 |
|---|---|
| 접수 담당 | 제출 파일 수신, 접수 점검, 접수 대장 기록, 문제 파일 격리, 기관과의 확인 |
| 집계 담당 | `aggregate.py` 실행, 입력 묶음 구성, 산출물 점검, 해석 초안 |
| 규칙·명세 검토 담당 | 규칙 이의와 값 집합 요청의 검토, 판정 초안, 규칙·명세 수정안 |
| 승인 담당 | 판정, 규칙 수정, 회신, 새 앱 버전 배포의 승인 |
| 배포 담당 | 새 앱 버전 빌드·게시([릴리스 절차](../docs/reproduce.md#릴리스-releasesh)), 기관 안내 |
| 기관 담당자 | 기관 쪽에서 검증 실행, 제출 전 확인, 피드백 작성 |

## 시작 전에 정할 것

아래는 코드나 저장소가 정하지 않았으므로 **운영 측이 정해 기관에 알립니다.** 정해지기 전까지는 표의 "미정"으로 두고 임의의 값을 안내하지 않습니다.

| 항목 | 현재 |
|---|---|
| 제출 전달 채널(어디로, 어떻게) | 미정 — 운영 정책으로 지정 |
| 기관 코드(기관을 부르는 이름) | 미정 — 운영 측이 부여 |
| 접수·집계·검토·승인 담당 지정 | 미정 — 운영 정책으로 지정 |
| 이의 판정과 규칙 수정의 승인 권한자 | 미정 — 운영 정책으로 지정 |
| 받은 파일과 산출물의 보관 기간·보관 위치·폐기 방법 | 미정 — 기관·운영 정책으로 지정 |
| 환자 정보가 든 파일을 받았을 때의 보고·처리 절차 | 미정 — 기관·운영 정책을 따름 |
| 기관 문의 창구와 응답 시한 | 미정 — 운영 측이 기입 |
| 공식 접수·합격 기준 | 이 저장소에 없음. 필요하면 운영 정책으로 정함 |

## 1. 기관 온보딩

기관마다 다음을 전합니다.

1. 설치 파일(릴리스 페이지의 `K-AIPA-DQ-<버전>-…`)과 견본 데이터 안내 → [설명서](../manual/README.md)
2. [README](README.md)와 [feedback.md](feedback.md)
3. 부여한 **기관 코드**, **전달 채널**, **문의 창구**(위 표가 정해진 뒤)
4. 보내는 것(`submission.json`)과 **보내지 않는 것**(`findings.csv`, `sufficiency.csv`, `input/`, 테이블 파일, 내보내기 폴더째), 환자 정보 없는 피드백 규칙
5. 첫 실행은 **규칙을 조정하지 않은 표준 상태**로, 두 번째 실행 후에도 **둘 다** 보내고 어느 쪽이 첫 표준 실행인지 알릴 것

## 2. 접수 (제출마다)

### 보관 구조

받은 파일은 아래처럼 **입력 묶음(세트)별로 나눠** 둡니다. 세트가 곧 "한 번에 집계하는 단위"입니다.

```
intake/                          (저장소 밖, 접근 통제)
  baseline/        첫 표준 실행
    H01/
      LUNG_CANCER_20261116_123456789_submission.json
  after-fix/       수정 후 두 번째 실행 (표준 규칙 상태)
  adjusted/        규칙을 조정했거나 관리자 모드를 쓴 실행
  quarantine/      접수 점검에 걸린 파일 (집계하지 않음)
```

- `H01` 은 중앙이 부여한 기관 코드를 쓴다는 뜻의 예시입니다. 실제 코드는 운영 측이 정합니다.
- 받은 파일의 **내용은 고치지 않습니다.** 파일 이름은 보관 구조에 맞춰 바꿔도 되지만 받은 원래 이름과 받은 시각은 접수 대장에 남깁니다.
- 앱의 기본 저장 이름 `<실행 ID>_submission.json` 은 파일 이름에 실행 ID(`<코호트>_<날짜>_<시각>`)가 들어 있어 같은 기관의 파일을 구분합니다. 앱의 **결과 폴더로 내보내기**는 `<실행 ID>/submission.json` 구조로 내므로 기관이 폴더째 보내면 파일 이름이 모두 `submission.json` 이 됩니다. 접수 때 위 구조로 옮기면서 구분되는 이름을 붙입니다.

### 접수 점검표

파일마다 다음을 **텍스트 편집기나 아래 명령으로** 확인하고 접수 대장에 적습니다. 하나라도 걸리면 `quarantine/` 에 두고 집계하지 않으며 기관 담당자에게 확인합니다.

| 점검 | 내용 | 걸리면 |
|---|---|---|
| 환자·행 단위 키 없음 | 파일에 `"person_id":`, `"row_key":`, `"detail":` 같은 키가 없는가 (아래 명령) | **환자 정보 수신 절차**(아래)로 |
| 형식 | JSON 으로 열리는가, `schema` 가 `kai-dq-submission/` 로 시작하는가 | 도구가 건너뜀. 재제출 요청 |
| 필수 항목 | `cohort`, `run_id`, `generated_at`, `rules`, `violations`, `by_rule` 이 있는가 | 도구가 예외로 멈출 수 있음. 재제출 요청 |
| 코호트 | `cohort` 가 여섯 코드 중 하나인가 | 확인 |
| 앱 버전·규칙 묶음 | `app_version`, `rule_set.standard_hash` 가 같은 세트의 다른 파일과 같은가. 같은 세트에 둘 이상이면 어느 쪽이 맞는지 | 아래 "해시와 버전" |
| `rule_set` 있음 | 파일에 `rule_set` 이 있는가 | 없으면 **확인되지 않은 파일**(아래) |
| 식별 정보 | `label`, `rule_set` 의 변경 내용·규칙 id 에 환자·기관 내부 식별 정보가 없는가 | 기관과 확인, 집계 전 처리는 운영 정책 |
| 구분 | 이 파일이 첫 표준 실행인지, 수정 후 실행인지, 규칙 조정 실행인지 (기관이 알린 것과 `rule_set` 이 맞는가) | 세트를 바로잡음 |

```bash
# 환자 단위 키가 들어 있는 파일 찾기 (나오면 접수 중단)
grep -lE '"(person_id|row_key|detail)"[[:space:]]*:' intake/baseline/*/*_submission.json

# 파일별 요약 보기
python - <<'EOF'
import json, glob
for p in sorted(glob.glob("intake/baseline/*/*_submission.json")):
    s = json.load(open(p, encoding="utf-8"))
    rs = s.get("rule_set") or {}
    h = rs.get("standard_hash")
    print(p, s.get("schema"), s.get("app_version"), s.get("cohort"), s.get("run_id"), s.get("generated_at"),
          h[:12] if h else "(rule_set 없음)", rs.get("admin_modified"), len(rs.get("disabled") or []), repr(s.get("label")))
EOF
```

(`note` 문장에 `person_id` 가 글자로 들어 있지만 따옴표 뒤에 `:` 가 붙은 키 형태는 아니므로 위 `grep` 에는 걸리지 않습니다.)

### 해시와 버전

- 집계 도구는 `schema` 접두사만 확인해 읽습니다. 앱 버전이 달라도, `standard_hash` 가 달라도 **자동으로 따로 분리하지 않습니다.** 해시가 둘 이상이면 `summary.md` 에 경고 한 줄을 남길 뿐입니다(터미널에는 나오지 않음).
- 따라서 **같은 세트에는 `app_version` 과 `standard_hash` 가 같은 파일만** 넣습니다. 다르면 세트를 나눠(`baseline-v1.0.0`, `baseline-v1.0.1` 처럼) 따로 집계하거나, 기관에 같은 버전으로 다시 실행해 달라고 요청합니다. 규칙 묶음이 다른 결과를 같은 규칙 id 로 합치면 뜻이 다른 규칙을 섞게 됩니다.
- 앱 버전은 달라도 해시가 같을 수 있고, 반대도 가능합니다. 둘 다 봅니다.

### 확인되지 않은 파일

`rule_set` 이 없는 파일(앱의 이전 형식 또는 편집된 파일)과 `origin` 이 없는 규칙 결과를 **도구 코드는 표준으로 간주합니다.** 그러나 운영상으로는 **표준 실행인지 확인되지 않은 것**입니다. 이런 파일은 `app_version` 으로 이전 판 여부를 확인하고, 기관에 표준 상태로 다시 실행해 보내도록 요청하는 것이 안전합니다. 확인될 때까지 기관 간 비교 세트에 넣지 않고 `quarantine/` 에 둡니다.

### 환자 정보 수신 절차

환자 ID·값이 든 파일(`findings.csv`, `sufficiency.csv`, `input/`, 테이블 파일, 값이 적힌 피드백이나 캡처)이 도착한 경우:

1. 더 열람하거나 복사·전달하지 않고 `quarantine/` 로 격리합니다.
2. 보낸 기관에 알리고, 집계에 쓰지 않습니다.
3. 이후의 보고·삭제 절차는 **기관과 파일럿 운영 정책**을 따릅니다. 이 문서는 절차의 세부나 담당자를 정하지 않습니다.

### 접수 대장

접수마다 한 줄. 환자 정보는 적지 않습니다.

| 항목 | 예 |
|---|---|
| 접수번호·접수일·접수 담당 | |
| 기관 코드, 코호트 | |
| 받은 원래 파일 이름, 보관 위치(세트) | |
| `run_id`, `generated_at`, `app_version`, `standard_hash` 앞부분 | |
| 구분(첫 표준·수정 후·규칙 조정)과 확인 방법 | |
| 점검 결과(통과·격리·재제출 요청) | |

## 3. 집계

### 명령

세트마다 따로 실행하고 출력 폴더도 따로 둡니다.

```bash
python pilot/aggregate.py intake/baseline/*/*_submission.json --out <저장소 밖 폴더>/out-baseline
python pilot/aggregate.py intake/after-fix/*/*_submission.json --out <저장소 밖 폴더>/out-after-fix
python pilot/aggregate.py intake/adjusted/*/*_submission.json  --out <저장소 밖 폴더>/out-adjusted
```

셸이 `*` 를 펼쳐 주지 않는 환경(Windows 명령 프롬프트)에서는 파일 경로를 직접 나열합니다. 도구는 폴더를 입력받아 안을 뒤질 수도 있지만 **이름이 정확히 `submission.json` 인 파일만** 찾습니다(`LUNG_CANCER_…_submission.json` 같은 이름은 잡히지 않음). 위 보관 구조에서는 파일 경로를 직접 넘기는 방식을 씁니다.

### 기관 이름이 정해지는 방식

도구는 기관 이름을 **파일이 든 바로 위 폴더 이름**으로 정합니다. 보관 구조(`intake/<세트>/<기관 코드>/<파일>`)를 따르면 폴더 이름이 곧 기관 코드가 되어 따로 지정할 필요가 없습니다. 구조가 다르면 다음 실수가 생깁니다.

- 앱의 내보내기 구조(`<실행 ID>/submission.json`)를 그대로 넘기면 **기관 이름이 실행 ID 로 나옵니다.** 같은 기관의 파일이 서로 다른 기관으로 집계됩니다.
- 한 폴더에 여러 기관의 파일을 모아 넘기면 **폴더 이름 하나가 기관 이름이 되어** 서로 덮어씁니다.

이럴 때는 `--name "<파일 경로>=<기관>"` 으로 파일마다 기관을 지정합니다. **경로 문자열이 명령줄에 넘긴 파일 경로와 글자 그대로 같아야** 합니다.

```bash
python pilot/aggregate.py \
    intake/baseline/siteA_lung.json intake/baseline/siteB_lung.json \
    --out <저장소 밖 폴더>/out-baseline \
    --name "intake/baseline/siteA_lung.json=H01" \
    --name "intake/baseline/siteB_lung.json=H02"
```

- `./intake/...` 처럼 앞에 `./` 를 붙이거나 구분자가 다르면 **경고 없이 무시**되고 폴더 이름이 쓰입니다.
- 경로에 `=` 가 들어 있는 파일에는 쓸 수 없습니다.
- 실행 뒤 `sites.csv` 의 `기관` 열이 의도한 기관 코드인지 반드시 봅니다.

### 도구가 하는 일과 하지 않는 일

| 하는 일 | 하지 않는 일 |
|---|---|
| `schema` 가 `kai-dq-submission/` 로 시작하는 파일만 읽음 (아니면 건너뛰고 표준오류에 알림) | 앱 버전·`standard_hash` 가 다른 제출분을 갈라 놓음 (해시가 둘 이상이면 `summary.md` 에 경고만) |
| 기관×코호트마다 **가장 늦은 `generated_at` 하나**만 사용 | 밀려난 이전 실행이 있다고 알려 줌. 이전 실행은 **어떤 산출물에도 나타나지 않음** |
| `rule_set` 이 없으면 표준으로, `origin` 이 없으면 표준으로 간주 | 그 간주가 사실인지 확인 |
| 출처가 표준이고 꺼지지 않은 규칙만 기관 간 비교에 사용, 나머지는 `nonstandard_rules.csv` | 규칙 설정을 바꾼 실행을 자동으로 별도 세트로 분리 (그 실행의 표준 출처 규칙은 비교에 그대로 들어감) |
| 파일의 필수 항목이 없으면 오류로 멈출 수 있음 | 파일의 서명·진본 확인 |

### 가장 늦은 실행만 쓴다는 것

같은 기관·같은 코호트의 파일이 한 번에 여러 개 들어가면 **가장 늦은 실행 하나만 남습니다.** 첫 실행(수정 전)과 수정 후 실행을 같이 넣으면 수정 후 실행만 집계되고 첫 실행은 조용히 사라집니다. 규칙을 조정한 실행이 가장 늦은 실행이면 그 기관·코호트의 표준 결과도 그 실행의 값으로 바뀝니다. 그러므로:

- **세트(baseline / after-fix / adjusted)마다 따로 집계합니다.** 기관×코호트당 파일이 하나씩만 들어가게 하는 것이 가장 안전합니다.
- baseline 과 after-fix 의 비교는 두 산출물(`out-baseline`, `out-after-fix`)을 나란히 놓고 합니다.
- 실행 뒤 `sites.csv` 의 `실행ID` 가 의도한 파일의 `run_id` 인지 봅니다.

### 산출물 점검 순서

1. 터미널 마지막 두 줄(기관·코호트 수, 모든 곳에서 우는 규칙 수)이 접수 대장과 맞는가.
2. `summary.md` **위에서부터**: 표의 행 수, 해시 경고(`standard_hash` 가 N가지) 유무, "규칙 설정이 표준이 아닌 실행" 절.
3. `sites.csv`: `기관`·`코호트`·`실행ID`, `건너뜀`·`오류`가 0 이 아닌 곳, `규칙설정`과 꺼진·바꾼·사용자·관리자 규칙 수.
4. `sufficiency_by_site.csv` 와 `summary.md` 의 데이터 충실도 절: 기관·코호트별 충족 비율입니다. 규칙 위반과 별개의 축이며 합격·불합격 기준이 아니므로, 비율이 낮은 곳은 기록 없음의 원인을 기관에 확인하되 원인을 단정하지 않습니다.
5. 그다음에야 `rules_summary.csv` 와 `summary.md` 의 규칙 표를 읽습니다.

## 4. 결과 읽기

### 분모는 기관×코호트 조합입니다

규칙마다 "실행한 곳"은 **기관×코호트 조합**의 수입니다. 같은 기관이 두 코호트를 냈으면 조합은 둘입니다. 그래서:

- `summary.md` 와 `rules_summary.csv` 의 "기관 수", "실행기관수", "실패기관수" 열은 **기관이 아니라 기관×코호트 조합 수**입니다.
- "모든 곳에서 우는 규칙"은 그 규칙을 실행한 조합이 **2개 이상**이고 **전부 실패**한 경우입니다. 실행한 조합이 2개여도 같은 기관의 두 코호트일 수 있으니 기관 수를 따로 확인합니다.
- "한 곳에서만 우는 규칙"은 실행한 조합이 2개 이상이고 그중 **하나만** 실패한 경우입니다.
- 코호트마다 적용되는 규칙이 다르므로(253~294개) 규칙마다 분모가 다릅니다. 조합이 1개뿐인 규칙은 위 두 목록에 들어가지 않습니다.

### 숫자와 상태

- `rules_by_site.csv` 의 칸: 실패는 위반 건수, 통과는 `0`, 건너뜀은 `-`, 실행 오류는 `!`. **빈 칸은 통과가 아닙니다.** 그 조합에 해당 규칙이 없거나, 꺼졌거나 조정되어(비표준) 이 표에서 빠진 것입니다.
- **건너뜀(`-`)·실행 오류(`!`)·꺼짐은 통과가 아니라 검사되지 않은 것**입니다. 위반 0건을 "문제없음"으로 읽지 않습니다.
- `rules_summary.csv` 의 `위반율%` 는 실행한 조합들의 (위반 합계 ÷ 검사 행 합계)입니다. 환자 비율이 아니며 기관 평균도 아닙니다.
- `sites.csv` 의 위반 합계는 오류와 경고를 합친 (규칙, 행) 쌍의 수이고, 한 행이 여러 규칙에 걸리면 중복해서 셉니다. 기관 간 전체 위반 건수 비교를 "품질 순위"로 쓰지 않습니다.
- "모든 곳에서 우는" 규칙은 규칙·명세를 먼저 의심하고, "한 곳에서만 우는" 규칙은 그 기관의 내보내기·관행을 먼저 의심합니다. 이것은 **가설**이며 판정이 아닙니다.

## 5. 이의 판정

기관의 이의(`feedback.md`, `feedback_rules.csv`)와 집계 결과를 묶어 규칙마다 판정을 기록합니다. 아래 필드와 상태는 **중앙이 별도 시트(예: [`adjudication.csv`](adjudication.csv) 헤더로 만든 표)에서 관리하는 운영 양식의 제안**입니다. **앱과 `aggregate.py` 에는 이 필드를 만들거나 저장하는 기능이 없으며** 새 기능을 뜻하지 않습니다.

### 필드

| 필드 | 내용 |
|---|---|
| 접수번호·접수일 | 중앙이 붙이는 번호와 날짜 |
| 기관 코드·코호트 | 이의를 낸 곳 |
| 제출 파일(세트/파일명), 실행 ID, 앱 버전, `standard_hash` | 어느 제출분을 근거로 보는지 |
| 규칙 ID | 이의 대상 (`USR-`·`ADM-` 규칙은 표준 판정 대상이 아님) |
| 기관 판정 | 오탐 / 정탐이지만 못 고침 / 모르겠음 (기관의 의견) |
| 규칙이 실행된 기관×코호트 수 / 그중 실패 수 / 위반율% | `rules_summary.csv` 의 값 |
| 중앙 판정 상태 | 아래 상태 중 하나 |
| 조치 유형 | 규칙 수정 · 심각도 변경 · 허용 코드(값 집합) 추가 · 명세 문의 · 안내문 수정 · 기관 내보내기 점검 · 조치 없음 |
| 근거 요약 | 판단 이유. **환자 정보 없이** |
| 결정일, 판정 담당 역할 | 누가(역할) 언제 판단했는지 |
| 승인 역할·승인일 | 승인이 필요하면 그 기록 (권한자는 운영 정책) |
| 반영 앱 버전, 회신일 | 수정이 반영된 버전과 기관에 알린 날 |

### 상태

| 상태 | 뜻 |
|---|---|
| 접수 | 받았고 아직 보지 않음 |
| 검토중 | 규칙·명세 검토 담당이 보는 중 |
| 추가 확인 요청 | 기관에 값 없이 답할 수 있는 질문을 보냄 |
| 수용 | 규칙·명세·값 집합을 고치기로 함 (승인 필요 여부는 운영 정책) |
| 부분 수용 | 일부만 고치거나 심각도만 조정 등 |
| 기각 | 규칙이 맞고 데이터 쪽 조치가 필요함. 근거 회신 |
| 보류 | 근거가 부족하거나 의뢰사 매뉴얼 해석이 필요해 다음 판으로 미룸 |
| 종결 | 반영 또는 기각 사유를 기관에 회신함 |

### 판단 지침 (참고)

- 여러 기관·코호트에서 같은 규칙이 우는 데다 기관들의 설명이 같은 방향이면 규칙이나 명세가 현장과 어긋났을 가능성이 큽니다.
- 한 기관에서만 울면 그 기관의 내보내기·기록 방식을 먼저 확인합니다.
- 조정한(꺼진·바뀐) 규칙과 그 이유는 표준 규칙을 고칠 근거로 쓰되, 조정 상태의 결과를 표준 결과로 합치지 않습니다.
- `정탐이지만 못 고침` 은 규칙을 바꿀 이유가 아니라 기관의 조치 문제로 다룹니다.
- 매뉴얼(2026-11-16)에 적힌 것의 위반을 임의로 완화하는 수정은 의뢰사 매뉴얼의 해석 문제이므로 보류로 두고 운영 정책에 따라 결정합니다.

## 6. 회신과 배포

1. 규칙마다 판정과 근거를 정리해 기관에 회신합니다(환자 정보 없이). 회신 채널은 운영 정책으로 정한 것을 씁니다.
2. 규칙·명세·값 집합의 수정은 **새 앱 버전**으로 반영됩니다. 앱에 자동 업데이트가 없으므로 기관이 새 설치 파일을 받아 설치합니다. 배포 일정과 방식은 운영 정책으로 정합니다.
3. 새 버전 이후의 제출분은 `app_version` 과 `standard_hash` 로 이전 제출분과 구분하고 **같은 세트에 섞지 않습니다.**
4. 이전 판(Quality Validator, v0.x)으로 만든 제출분은 규칙 묶음이 다를 수 있으므로 위와 같이 별도 세트로 다룹니다. 앱에서 이전 규칙 묶음을 골라 다시 돌리는 기능은 없습니다.
