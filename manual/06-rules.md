# 6. 규칙 편집

표준 규칙 390개는 의뢰사 매뉴얼(2026-11-16)과 보완 검토 규칙으로 구성됩니다. 기관의 코드 체계나 관행 때문에 어떤 규칙이 맞지 않거나, 기관이 따로 점검하고 싶은 항목이 있으면 **검증 규칙 관리** 화면에서 규칙을 조정할 수 있습니다. 조정은 네 수준이고, 수준 1~3 은 누구나, 수준 4 는 관리자 모드에서만 편집할 수 있습니다.

**원칙은 하나입니다. 표준과 다르게 실행했다면 그 사실이 결과에 반드시 남습니다.** 보고서, 규칙별 결과 파일, 중앙 제출 파일에 모두 기록되므로 조정을 숨길 수 없고, 중앙은 표준 규칙으로 돌린 결과와 따로 집계합니다.

| 수준 | 누가 | 할 수 있는 것 |
|---|---|---|
| 1 | 누구나 | 규칙 **켜기/끄기** |
| 2 | 누구나 | **심각도** 바꾸기(오류 ↔ 경고), 값 **범위·정규식·허용 코드** 조정 |
| 3 | 누구나 | **양식으로 규칙 추가** (SQL 없이): `USR-###` 규칙 |
| 4 | 관리자 모드 | 교차 규칙의 **SQL 직접 수정**, **SQL 로 새 규칙 추가** (`ADM-###`) |

## 수준 1: 규칙 켜고 끄기

**검증 규칙 관리** 화면에서 규칙을 찾아 끕니다. 끈 규칙은 실행하지 않고, 결과에는 `꺼짐`(위반 0건)으로 남습니다. 규칙이 코호트 구성상 적용되지 않는 것(예: SACT 표가 없는 코호트의 SACT 규칙)과는 다릅니다. 꺼진 규칙 수는 `summary.json` 의 `rules_disabled` 에 집계됩니다.

언제 끄나요: 기관이 그 항목을 원천 시스템에서 구할 수 없고, 매번 같은 위반이 나서 다른 위반이 묻힐 때. 규칙이 틀렸다고 생각하면 끄는 데서 그치지 말고 규칙 id 와 이유를 파일럿 피드백으로 알려 주세요.

## 수준 2: 심각도와 값 조정

- **심각도**: 오류(error) 와 경고(warning) 사이를 바꿉니다. 매뉴얼에 적힌 것의 위반은 기본이 오류, 매뉴얼 밖 제약은 기본이 경고입니다.
- **값 범위**: 범위 규칙의 최솟값·최댓값(예: `age_at_index` 0~110)을 기관의 실제 범위에 맞춥니다.
- **정규식**: 형식 규칙의 패턴을 조정합니다. 올바른 정규식이어야 저장됩니다.
- **허용 코드**: OMOP 대표 코드 집합을 검사하는 규칙(`*_concept_id` 코드표, 경고)에 기관의 코드를 추가합니다. 추가한 코드는 허용 집합에 더해집니다(기존 코드는 그대로).

## 수준 3: 양식으로 규칙 추가

SQL 을 쓰지 않고 **표 · 필드 · 검사 유형**을 골라 규칙을 만듭니다. id 는 `USR-001`, `USR-002` … 로 자동 부여됩니다.

| 검사 유형 | 입력 | 뜻 |
|---|---|---|
| 필수값 (`not_null`) | | 이 필드는 비어 있으면 안 됨 |
| 범위 (`range`) | 최솟값, 최댓값 | 값이 범위 안이어야 함 |
| 코드 목록 (`codelist`) | 허용 코드들 | 값이 목록에 있어야 함 |
| 형식 (`pattern`) | 정규식 | 값이 패턴에 맞아야 함 |
| 미래 날짜 금지 (`not_future`) | | 검증 실행일 이후 날짜가 아니어야 함 |

규칙마다 이름, 심각도, 설명(선택)을 붙입니다. 사용자 규칙은 표준 구조 규칙과 같은 방식으로 실행되고 위반은 같은 화면에서 조회됩니다. 사용자 규칙은 표준 규칙이 아니므로 결과의 규칙 출처(`origin`)가 `custom` 으로 표시됩니다.

## 수준 4: 관리자 모드 (SQL)

교차 규칙은 DuckDB SQL 로 작성되어 있습니다. 이 SQL 을 고치거나 새 SQL 규칙을 만드는 것은 **관리자 모드**에서만 할 수 있습니다.

1. **설정** 화면의 **관리자 모드 켜기** 단추를 눌러 켭니다. 비밀번호는 없습니다. 실수로 SQL 을 건드리는 일을 막는 확인 단계이며 접근 통제 장치가 아닙니다. 켜 있는 동안 화면 위쪽에 '관리자 모드' 띠가 표시됩니다.
2. **검증 규칙 관리** 화면에서 표준 교차 규칙의 SQL 을 수정하거나, **SQL 규칙 추가 (관리자)** 로 새 규칙을 만듭니다(id `ADM-001`, `ADM-002` …). 새 규칙은 분류(적합성·완전성·타당성), 심각도, 적용 코호트(전체 또는 지정), 필요한 표, SQL 을 정합니다.
3. SQL 은 위반 행을 `person_id`, `row_key`, `detail` 세 컬럼으로 돌려줘야 합니다. 표 이름은 명세의 표 이름을 그대로 쓰고, `{TODAY}`(검증 실행일), `{DISEASE}`(질환 본표), `{DISEASE_PK}`(질환 본표 키) 치환자를 쓸 수 있습니다. 저장하기 전에 **시험 실행** 으로 앱에 내장된 견본(clean · dirty)에 돌려 보며, **시험 후 저장** 으로 저장합니다.
   반환 열은 결과가 0행이어도 검사합니다. 세 이름은 각각 한 번만 있어야 하며 추가 열은 허용하지 않습니다. 열 순서는 달라도 이름으로 연결합니다.
4. 관리자 모드를 끄면 SQL 을 더 고칠 수 없습니다. 이미 만든 SQL 변경과 `ADM-###` 규칙은 그대로 유지되어 계속 실행되고, 결과에는 관리자 출처(`admin`)로 기록됩니다. 되돌리려면 **SQL 만 표준으로** 또는 **이 규칙만 표준으로 되돌리기**를 씁니다.

관리자 모드의 SQL 은 사용자 컴퓨터의 데이터에 대해서만 실행됩니다. 그래도 규칙의 의미를 바꾸는 일이므로 표준 규칙의 결과와 직접 비교할 수 없게 됩니다.

## 조정은 어디에 남나요

| 위치 | 내용 |
|---|---|
| `report.md` 의 `## 규칙 설정` | 조정이 있거나 관리자 모드를 쓴 실행에만 붙는 절. **표준 규칙 묶음 해시**와 **실제 사용한 규칙 묶음 해시**, 관리자 모드 사용 여부, 바뀐 규칙의 표(규칙 id · 출처 · 변경 내용) |
| `rule_results.csv` 의 `origin` 열 | 규칙마다 표준(`standard`) · 변경(`modified`) · 사용자(`custom`) · 관리자(`admin`) 구분 |
| `submission.json` 의 `rule_set` | `standard_hash`, `effective_hash`, `admin_mode`(관리자 모드를 켠 채 실행했는지), `admin_modified`(SQL 을 바꾸거나 `ADM-###` 규칙이 있는지 — 관리자 모드를 켰다는 것만으로는 아님), `disabled`(꺼진 규칙 id), `modified`(바꾼 규칙 id 와 변경 내용), `custom`(사용자 규칙 id), `admin`(관리자 규칙 id) |
| 규칙 설정 파일과 변경 이력 | 이 PC 의 앱 데이터 폴더에 `rule-overrides.json`(현재 설정, 표준과 다른 부분만)과 `rule-history.jsonl`(설정을 바꿀 때마다 언제·어느 규칙을·어떻게 바꿨는지, 관리자 모드를 켜고 끈 시각까지 한 줄씩 추가) 가 남음. **검증 규칙 관리**의 **변경 이력** 단추로 볼 수 있고, **설정 내보내기·가져오기** 로 다른 PC 에 옮길 수 있음 |

해시는 실제 규칙, 명세, 허용 코드 값, 보조 concept 목록, 코호트 구성을 함께 포함하는 지문입니다(`kai-ruleset-hash/2`). `standard_hash` 와 `effective_hash` 가 같으면 그 설치본의 표준 그대로 실행한 것입니다. 해시에는 환자 데이터를 넣지 않습니다. 이전 해시 형식의 결과와는 직접 비교하지 말고 같은 기준으로 다시 실행하세요.

## 중앙에서는 어떻게 다루나요

중앙은 `submission.json` 의 `rule_set` 과 규칙별 출처(`origin`)를 보고 나눕니다. 출처가 표준인 규칙의 결과만 기관 간 비교(어떤 규칙이 여러 기관에서 우는가)에 쓰고, 끈 규칙과 조정한 규칙, 사용자 규칙, 관리자 규칙의 결과는 **따로 집계**합니다. SQL 을 바꾼 실행(`admin_modified`)은 규칙의 뜻 자체가 달라졌으므로 별도로 표시합니다. 그러니 조정은 필요하면 얼마든지 하되, 그 설정으로 낸 결과를 표준 결과로 보내지 마세요. 파일을 고치지 말고 `submission.json` 을 그대로 보내면 됩니다.

## 표준으로 되돌리기

규칙 하나는 **이 규칙만 표준으로 되돌리기**로, 설정 전체는 **모두 표준으로 되돌리기**로 표준 규칙 묶음에 되돌립니다(사용자 규칙과 관리자 SQL 도 삭제됩니다). 이때 실행 결과의 `effective_hash` 는 `standard_hash` 와 같아지고 `## 규칙 설정` 절은 붙지 않습니다. 되돌리는 것도 변경 이력에 남습니다.
