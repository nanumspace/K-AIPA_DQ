# 6. 규칙 편집

표준 규칙 440개는 의뢰사 매뉴얼(2026-11-16)과 보완 검토 규칙으로 구성됩니다. 기관의 코드 체계나 관행 때문에 어떤 규칙이 맞지 않거나, 기관이 따로 점검하고 싶은 항목이 있으면 **검증 규칙 관리** 화면에서 규칙을 조정할 수 있습니다. 조정은 네 수준이고, 수준 1~3 은 누구나, 수준 4 는 관리자 모드에서만 편집할 수 있습니다.

**원칙은 하나입니다. 표준과 다르게 실행했다면 그 사실이 결과에 남습니다.** 보고서, 규칙별 결과 파일, 중앙 제출 파일에 모두 기록되므로 일반 사용 중에는 조정이 결과에 드러납니다. 중앙은 표준 규칙으로 돌린 결과와 따로 집계합니다. 다만 이 기록은 **사용자가 정직하게 보낸다는 전제의 표시**이며, 위·변조를 막거나 사람을 확인하는 장치가 아닙니다(아래 "기록의 한계").

| 수준 | 누가 | 할 수 있는 것 |
|---|---|---|
| 1 | 누구나 | 규칙 **켜기/끄기** |
| 2 | 누구나 | **심각도** 바꾸기(오류 ↔ 경고), 값 **범위·정규식·허용 코드** 조정 |
| 3 | 누구나 | **양식으로 규칙 추가** (SQL 없이): `USR-###` 규칙 |
| 4 | 관리자 모드 | 교차 규칙의 **SQL 직접 수정**, **SQL 로 새 규칙 추가** (`ADM-###`) |

"누구나"는 이 PC 에서 앱을 쓰는 사람 누구나라는 뜻입니다. 앱에는 계정·권한 구분이 없습니다. 누가 규칙을 조정할 수 있는지는 기관이 정합니다.

## 저장과 이동

- **즉시 적용**: 사용 여부와 심각도는 바꾸는 즉시 저장됩니다.
- **저장해야 적용**: 범위·패턴·추가 코드·SQL·사용자 규칙 양식은 저장 단추를 눌러야 적용됩니다. 범위·패턴·코드는 저장 전 현재 값·저장 후 값·표준 값을 비교합니다.
- 저장하지 않은 내용이 있으면 다른 규칙 선택, 상세 닫기, 메뉴 이동, 편집 창 닫기·바깥 클릭·Escape에서 버릴지 확인합니다. **취소**하면 입력을 유지합니다. 즉시 적용 항목을 바꿔도 작성 중인 범위·SQL을 조용히 지우지 않습니다.
- 편집 창은 Tab으로 내부 항목을 이동하고 Escape로 닫습니다. 닫으면 열기 전 버튼으로 초점이 돌아갑니다.

## 적용 명세 조회

**검증 규칙 관리 → 적용 명세 · 컬럼별 규칙 보기**에서 테이블, 컬럼 자료형, 필수 Y/N, 설명, 참조, 범위, 코드표와 허용 코드를 확인합니다. 연결된 규칙 버튼을 누르면 기존 규칙 관리에서 해당 규칙의 상세와 기관 조정을 확인합니다. 교차 테이블 규칙은 해당 테이블에 공통으로 관련된 규칙입니다.

## 검증 기준 패키지

기본 명세와 규칙은 설치본에 포함되므로 별도 파일 없이 실행할 수 있습니다. `spec/`, `rules/` 폴더를 직접 만들거나 선택하지 않습니다.

1. 중앙 운영자가 공식 배포 경로로 제공한 **검증 기준 패키지 ZIP**을 받습니다.
2. **설정 → 검증 기준 패키지 → 기준 패키지 가져오기**에서 ZIP 하나를 선택합니다.
3. 앱이 지원 형식·필수 파일·지문·명세/규칙 참조·호환성을 검사한 뒤 기준 이름, 배포자 표기, 매뉴얼, 구성과 변경 사항을 보여 줍니다. 배포자 표기와 지문은 출처를 인증하지 않으므로 공식 배포 경로를 확인하세요.
4. 기존 기관 조정과 충돌하지 않으면 조정을 유지합니다. 충돌하면 **취소**하거나, **기관 조정 전체 초기화**에 명시적으로 동의한 뒤 적용합니다. 초기화 전 내용은 변경 이력에 남습니다. 규칙 ID가 같다는 이유만으로 변경된 규칙에 이전 조정을 조용히 재적용하지 않습니다.
5. **확인한 기준 적용**을 누르면 다음 실행부터 사용합니다. 받은 ZIP을 옮기거나 지워도 앱 내부 사본을 사용합니다. 검증 실행 중에는 기준을 바꿀 수 없습니다.

**현재 기준 패키지 내보내기**는 명세·구조/교차 규칙·코드표·보조 concept·코호트 구성·제약과 배포 정보를 함께 저장합니다. 환자 데이터와 기관 조정은 포함하지 않습니다. 기관 조정만 다른 PC에 옮기는 기존 **설정 내보내기·가져오기(JSON)**와 다릅니다. YAML 직접 편집 화면과 과거 모델 선택 기능은 제공하지 않습니다.

### 실행 당시 기준 보관

1.0.1부터 실행마다 `criteria.zip`(당시 기본 YAML 전체)과 `criteria-snapshot.json`(당시 명세·실효 규칙·기관 조정·기준일·해시·관리자 모드)을 보관합니다. 엔진도 이 실행 전용 사본을 읽습니다. **결과 보고서 → 실행 당시 적용 기준**과 **위반 상세 → 기대 조건**은 현재 설정이 아니라 보관한 내용을 사용합니다.

원본이 보관되지 않은 이전 실행은 그 사실을 표시하며 현재 규칙으로 대신 설명하지 않습니다. 두 파일에는 기관 규칙 설명·SQL 등이 포함될 수 있으므로 기관 내부에 보관하고 외부 제출하지 않습니다. **결과 묶음 저장**에는 두 파일도 포함됩니다. 중앙 제출은 기존처럼 `submission.json`의 집계와 기준 메타데이터를 사용합니다. 로컬 파일 보관은 위·변조 방지 장치가 아닙니다.


## 수준 1: 규칙 켜고 끄기

**검증 규칙 관리** 화면에서 규칙을 찾아 끕니다. 끈 규칙은 실행하지 않고, 결과에는 `꺼짐`(`disabled`, 위반 0건)으로 남습니다. **꺼진 규칙은 통과가 아니라 검사하지 않은 것**입니다. 규칙이 코호트 구성상 적용되지 않는 것(예: SACT 표가 없는 코호트의 SACT 규칙)과는 다릅니다. 꺼진 규칙 수는 `summary.json` 의 `rules_disabled` 에 집계됩니다.

언제 끄나요: 기관이 그 항목을 원천 시스템에서 구할 수 없고, 매번 같은 위반이 나서 다른 위반이 묻힐 때. 규칙이 틀렸다고 생각하면 끄는 데서 그치지 말고 규칙 id 와 이유를 파일럿 피드백으로 알려 주세요(환자 정보 없이).

## 수준 2: 심각도와 값 조정

- **심각도**: 오류(error) 와 경고(warning) 사이를 바꿉니다. 매뉴얼에 적힌 것의 위반은 기본이 오류, 매뉴얼 밖 제약은 기본이 경고입니다.
- **값 범위**: 범위 규칙의 최솟값·최댓값(예: `age_at_index` 0~110)을 기관의 실제 범위에 맞춥니다.
- **정규식**: 형식 규칙의 패턴을 조정합니다. 올바른 정규식이어야 저장됩니다.
- **허용 코드**: OMOP 대표 코드 집합을 검사하는 규칙(`*_concept_id` 코드표, 경고)에 기관의 코드를 추가합니다. 추가한 코드는 허용 집합에 더해집니다(기존 코드는 그대로).

## 수준 3: 양식으로 규칙 추가

SQL 을 쓰지 않고 **표 · 필드 · 검사 유형**을 골라 규칙을 만듭니다. id 는 `USR-001`, `USR-002` … 로 자동 부여됩니다.

| 검사 유형 | 입력 | 뜻 |
|---|---|---|
| 필수값 (`not_null`) | | 이 필드는 비어 있으면 안 됨 |
| 범위 (`range`) | 최솟값, 최댓값 | 값이 범위 안이어야 함 |
| 코드 목록 (`codelist`) | 허용 코드들 | 값이 목록에 있어야 함 |
| 형식 (`pattern`) | 정규식 | 값이 패턴에 맞아야 함 |
| 미래 날짜 금지 (`not_future`) | | 검증 기준일 이후 날짜가 아니어야 함 |

규칙마다 이름, 심각도, 설명(선택)을 붙입니다. 사용자 규칙은 표준 구조 규칙과 같은 방식으로 실행되고 위반은 같은 화면에서 조회됩니다. 사용자 규칙은 표준 규칙이 아니므로 결과의 규칙 출처(`origin`)가 `custom` 으로 표시됩니다. 규칙 이름·설명은 결과 파일에 실리므로 환자 정보를 넣지 않습니다.

## 수준 4: 관리자 모드 (SQL)

교차 규칙은 DuckDB SQL 로 작성되어 있습니다. 이 SQL 을 고치거나 새 SQL 규칙을 만드는 것은 **관리자 모드**에서만 할 수 있습니다.

1. **설정** 화면의 **관리자 모드 켜기** 단추를 눌러 켭니다. **비밀번호도 사용자 확인도 없습니다.** 실수로 SQL 을 건드리는 일을 막는 확인 단계(처음 켤 때 안내 창)이며 **접근 통제나 권한 부여 장치가 아닙니다.** 앱을 다시 열면 꺼진 채로 시작합니다. 켜 있는 동안 화면 위쪽에 '관리자 모드' 띠가 표시됩니다.
2. **검증 규칙 관리** 화면에서 표준 교차 규칙의 SQL 을 수정하거나, **SQL 규칙 추가 (관리자)** 로 새 규칙을 만듭니다(id `ADM-001`, `ADM-002` …). 새 규칙은 분류(적합성·완전성·타당성), 심각도, 적용 코호트(전체 또는 지정), 필요한 표, SQL 을 정합니다.
3. SQL 은 위반 행을 `person_id`, `row_key`, `detail` 세 컬럼으로 돌려줘야 합니다. 표 이름은 명세의 표 이름을 그대로 쓰고, `{TODAY}`(검증 기준일), `{DISEASE}`(질환 본표), `{DISEASE_PK}`(질환 본표 키) 치환자를 쓸 수 있습니다. 저장하기 전에 **시험 실행**으로 내장 견본(clean · dirty)에 돌려 보며, **시험 후 저장**으로 저장합니다. SQL 실행 오류와 데이터 위반 건수를 구별해서 확인하세요.
   반환 열은 결과가 0행이어도 검사합니다. 세 이름은 각각 한 번만 있어야 하며 추가 열은 허용하지 않습니다. 열 순서는 달라도 이름으로 연결합니다.
4. 관리자 모드를 끄면 SQL 을 더 고칠 수 없습니다. 이미 만든 SQL 변경과 `ADM-###` 규칙은 그대로 유지되어 계속 실행되고, 결과에는 관리자 출처(`admin`)로 기록됩니다. 되돌리려면 **SQL 만 표준으로** 또는 **이 규칙만 표준으로 되돌리기**를 씁니다.

관리자 모드의 SQL 은 사용자 컴퓨터의 데이터에 대해서만 실행됩니다. 그래도 규칙의 의미를 바꾸는 일이므로 표준 규칙의 결과와 직접 비교할 수 없게 됩니다. **누가 관리자 모드를 쓸 수 있는지, 쓰기 전에 승인이 필요한지는 기관 정책으로 정합니다.** 파일럿 기관에는 관리자 모드를 권하지 않습니다([파일럿 키트](../pilot/README.md)).

## 조정은 어디에 남나요

| 위치 | 내용 |
|---|---|
| `report.md` 의 `## 규칙 설정` | 조정이 있거나 관리자 모드를 쓴 실행에만 붙는 절. **표준 규칙 묶음 해시**와 **실제 사용한 규칙 묶음 해시**, 관리자 모드 사용 여부, 바뀐 규칙의 표(규칙 id · 출처 · 변경 내용) |
| `rule_results.csv` 의 `origin` 열 | 규칙마다 표준(`standard`) · 변경(`modified`) · 사용자(`custom`) · 관리자(`admin`) 구분 |
| `submission.json` 의 `rule_set` | `standard_hash`, `effective_hash`, `admin_mode`(관리자 모드를 켠 채 실행했는지), `admin_modified`(SQL 을 바꾸거나 `ADM-###` 규칙이 있는지 — 관리자 모드를 켰다는 것만으로는 아님), `disabled`(꺼진 규칙 id), `modified`(바꾼 규칙 id 와 변경 내용), `custom`(사용자 규칙 id), `admin`(관리자 규칙 id) |
| 규칙 설정 파일과 변경 이력 | 앱 데이터 폴더의 `rule-overrides.json`(내장 기준 조정) 또는 `criteria-settings/<기준별 ID>/rule-overrides.json`(가져온 기준 조정), 공통 `rule-history.jsonl`(기준 적용과 설정 변경 전후·관리자 모드 기록). **변경 이력**, **설정 내보내기·가져오기**로 조회·이동 |

### 기록의 한계

- **변경 이력은 위·변조 방지 기록이 아닙니다.** `rule-history.jsonl` 은 이 PC 의 일반 텍스트 파일이므로 고치거나 지울 수 있습니다. 감사 증적으로 쓰려면 기관이 별도로 보관·통제해야 합니다.
- **이력에는 누가 바꿨는지(사용자 신원)와 누가 승인했는지가 없습니다.** 시각, 동작, 규칙, 바꾸기 전후 값, 관리자 모드 여부만 남습니다. 이 프로그램은 사용자를 구분하지 않습니다.
- **관리자 모드의 단추와 관리자 모드 사용 표시는 인증·승인이 아닙니다.** `admin_mode: true` 는 그 실행이 관리자 모드가 켜진 상태였다는 사실의 표시일 뿐, 권한 있는 사람이 승인했다는 뜻이 아닙니다.
- **해시는 파일의 진본이나 무결성을 증명하지 않습니다.** 해시는 실제 규칙, 명세, 허용 코드 값, 보조 concept 목록, 코호트 구성을 함께 포함하는 지문입니다(`kai-ruleset-hash/2`). `standard_hash` 와 `effective_hash` 가 같으면 그 설치본의 표준 그대로 실행한 것이라는 표시일 뿐, `submission.json` 파일이 위조되지 않았다는 증명은 아닙니다(파일에 서명이 없습니다). 해시에는 환자 데이터를 넣지 않습니다. 이전 해시 형식의 결과와는 직접 비교하지 말고 같은 기준으로 다시 실행하세요.

## 중앙에서는 어떻게 다루나요

중앙은 `submission.json` 의 `rule_set` 과 규칙별 출처(`origin`)를 보고 나눕니다. 출처가 표준인 규칙의 결과만 기관 간 비교(어떤 규칙이 여러 기관에서 우는가)에 쓰고, 끈 규칙과 조정한 규칙, 사용자 규칙, 관리자 규칙의 결과는 **따로 집계**합니다. SQL 을 바꾼 실행(`admin_modified`)은 규칙의 뜻 자체가 달라졌으므로 별도로 표시합니다. 그러니 조정은 필요하면 얼마든지 하되, 그 설정으로 낸 결과를 표준 결과로 보내지 마세요. 파일을 고치지 말고 `submission.json` 을 그대로 보내면 됩니다.

다만 집계 도구는 위의 구분을 **제출 파일에 적힌 값 그대로** 따릅니다. 앱 버전이나 규칙 묶음이 서로 다른 제출분을 자동으로 갈라 주지는 않으며, `rule_set` 이 없는 파일(이전 형식)은 표준 실행으로 간주합니다. 그 점검은 중앙의 운영 절차로 합니다([중앙 운영 절차](../pilot/central-runbook.md)).

## 표준으로 되돌리기

규칙 하나는 **이 규칙만 표준으로 되돌리기**로 되돌립니다. 설정 전체 초기화는 화면 아래 **위험 구역**의 **모든 규칙을 표준으로 되돌리기…**를 사용합니다. 삭제될 변경·사용자 규칙·관리자 SQL 규칙 수를 확인하고 승인해야 하며, 미저장 입력이 있으면 따로 확인합니다. 성공하면 편집 패널을 닫고 표준 상태를 표시합니다. 실행 결과의 `effective_hash`는 `standard_hash`와 같아지고 되돌리기도 변경 이력에 남습니다.
