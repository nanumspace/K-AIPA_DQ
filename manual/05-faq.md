# 5. 자주 묻는 질문

## 범위

**이 프로그램으로 무엇을 검증하나요?**
여섯 질환(폐암·유방암·대장암·대사이상지방간·당뇨병·림프종) 임상 코호트 테이블이 의뢰사 매뉴얼(2026-11-16) 명세에 맞는지입니다. K-AIPA 사업이 다루는 전임상 데이터, 오믹스 데이터, AI 모델은 검증하지 않습니다.

**검증을 통과하면 임상 데이터로 인증받은 건가요?**
아닙니다. 위반 0건은 이 프로그램의 규칙을 어기지 않았다는 뜻일 뿐입니다. 임상적 적절성의 판정도, K-AIPA 나 의뢰사의 공식 접수·승인도 아닙니다. 보고서의 등급 표시(우수·양호·주의·위험)도 내부 점검용 구간이며 공식 기준이 아닙니다([4장](04-output.md)).

## 설치와 실행

**설치 파일을 실행하면 보안 경고가 뜹니다.**
설치 파일은 코드 서명과 공증이 되어 있어 정상 파일이면 경고가 뜨지 않습니다. 경고가 뜨면 내려받기 중 손상되었거나 Release 페이지가 아닌 곳에서 받은 파일입니다. Release 페이지에서 다시 받고, 필요하면 `SHA256SUMS.txt` 와 대조합니다.

**인터넷이 안 되는 PC에서도 되나요?**
됩니다. 명세와 규칙이 프로그램 안에 들어 있고 인터넷 연결 없이 동작합니다. 프로그램에는 데이터를 외부로 자동 전송하는 기능이 없습니다.

**실행 이력은 어디에 저장되나요?**
사용자 컴퓨터의 앱 데이터 폴더(Windows `%APPDATA%\Quality Validator`, macOS `~/Library/Application Support/Quality Validator`)에 저장됩니다. 위치는 **설정** 화면에서 볼 수 있습니다. 저장은 한 곳이 아니라 여러 군데입니다.

| 무엇 | 어디에 |
|---|---|
| 실행 요약, 규칙별 결과, 위반 행 목록 | `history.duckdb` (DuckDB 파일 하나) |
| 정규화된 입력 사본, 기본 출력 6종, 기준 ZIP·스냅샷, 정규화 기록 | `runs/<실행 ID>/` 폴더 |
| 내장 기준의 규칙 설정과 공통 변경 이력 | `rule-overrides.json`, `rule-history.jsonl` |
| 가져온 기준과 기준별 기관 조정 | `criteria-packages/`, `criteria-settings/` |
| 앱 설정(적용 기준, 검증 기준일 기본값 등) | `config.json` |

앱이 다른 곳으로 전송하지는 않습니다. 그러나 이 폴더에는 위반 행의 환자 ID 와 정규화된 입력 사본이 있어 환자 단위 정보가 들어 있습니다. 폴더 이름이 `Quality Validator` 인 것은 이전 판의 이력을 그대로 보이게 하려고 옛 이름을 유지한 것입니다([1장](01-install.md)).

**실행 이력을 백업하려면 어떻게 하나요? 삭제는요?**
- **백업**: 앱을 닫고 앱 데이터 폴더를 통째로 복사합니다(`history.duckdb` 와 `runs/` 와 규칙 설정이 함께 있어야 합니다). 백업본의 보관 위치·기간은 기관 정책에 따릅니다. 백업본에도 환자 단위 정보가 들어 있습니다.
- **실행 하나 삭제**: **통계 모니터링**의 **삭제**. DB 기록과 `runs/<실행 ID>/` 폴더를 지웁니다.
- **지워지지 않는 것**: 내보내기·다른 이름으로 저장한 사본, 이미 전달한 `submission.json`, 앱 데이터 폴더의 백업본, 앱을 지워도 남는 앱 데이터 폴더. 이런 사본은 따로 찾아서 지웁니다. 삭제는 되돌릴 수 없습니다.

**얼마나 큰 데이터까지 되나요?**
환자 2,000명, 행 50만(30MB) 규모를 10초 안팎에 처리합니다. 메모리는 1GB 미만을 씁니다. 그보다 크면 시간이 비례해 늘지만 나눠 넣을 필요는 없습니다.

## 입력 파일

**서식을 따로 채우고 변환해야 하나요?**
아닙니다. 질환 본표와 공통 표를 병원이 직접 채워 그대로 넣습니다. 서식을 따로 채워 바꾸는 단계는 없습니다.

**실행이 막힙니다. 무엇이 없나요?**
PERSON 과 해당 코호트의 질환 본표(예: `LUNG_CANCER`)가 없으면 막힙니다. 나머지 표가 없으면 '테이블 없음' 주의로 보고되고 그 표의 규칙은 건너뜁니다. 건너뛴 규칙은 통과가 아니라 **검사하지 않은 것**입니다. 사례가 없어도 헤더만 있는 빈 파일을 넣는 편이 좋습니다.

**예전 양식의 컬럼 이름이 경고나 오류로 나옵니다.**
컬럼 구성은 의뢰사 매뉴얼(2026-11-16)과 같아야 합니다. 항암요법 표는 `SACT`(키 `sact_id`)이고, 매뉴얼에 없는 컬럼은 '명세 외 컬럼' 경고, 있어야 할 컬럼이 없으면 '컬럼 누락' 오류입니다. 컬럼 별칭은 받지 않습니다. 앱이 주는 양식(엑셀 양식·CSV 양식 묶음·컬럼 명세서)으로 맞춥니다.

**어떤 기준으로 검증되나요? 규칙은 몇 개인가요?**
의뢰사 매뉴얼 2026-11-16 하나입니다. 규칙은 436개(구조 410 + 교차 26)이고 코호트마다 298~339개가 적용됩니다. 매뉴얼 보완인 선택 컬럼·선택 테이블 규칙은 해당 컬럼·표를 낸 경우에만 실행되고, 내지 않으면 건너뜁니다. 설정에서 고르는 판(版) 같은 것은 없어서, 앱 버전이 다르면 규칙 묶음이 다를 수 있습니다. 이전 판(v0.x) 이름의 앱으로 만든 실행 이력은 그대로 보이지만, 이전 규칙 묶음을 골라 다시 돌릴 방법은 없습니다. 결과가 어느 규칙 묶음으로 나왔는지는 `submission.json` 의 `app_version` 과 `rule_set.standard_hash` 로 구분합니다. 기관 사정에 맞게 규칙을 켜고 끄거나 조정할 수는 있으며, 그 경우 결과에 표준과 다르게 실행했다는 기록이 남습니다([6. 규칙 편집](06-rules.md)).

**concept_id 가 표준 개념인지 확인해 주나요?**
선택 표 CONCEPT 를 함께 내면 확인합니다(1.0.3). 낸 데이터에 쓴 개념만 담은 CONCEPT 일부를 넣으면 개념마다 CONCEPT 에 있는지, 표준·유효한지, 필드에 맞는 영역·어휘인지 경고로 알려 주고, VOCABULARY 를 넣으면 어휘 배포판(v20260829)도 확인합니다([2. 입력 파일 준비](02-input.md)의 "선택 컬럼과 선택 표"). 내지 않으면 앱에 어휘가 없으므로 존재·표준 여부는 검사하지 못하고 OMOP 코드 목록 대조(경고)만 합니다. 항종양제 판정(`sact_id` 연결 확인)은 앱에 내장된 항암제 목록을 쓰므로 목록 밖 약은 잡지 못합니다.

**테스트용 데이터가 있나요?**
있습니다. 앱의 **입력 양식 내려받기 → 견본 데이터**는 오류 없는 clean 데이터이고, GitHub Release 페이지의 **견본 데이터 zip**에는 오류를 주입한 dirty 데이터와 정답표, 환자 1명의 Good Sample 까지 들어 있습니다. clean 은 오류 등급(error) 위반 0건이 기대 결과이고, 대장암·림프종 clean 에는 경고 `SEM-SACT-006` 이 남을 수 있습니다(폴더의 README.txt 에 기대 건수가 있습니다). 모두 가상데이터이며 Good Sample 은 임상의의 감수를 받지 않은 구조 예시입니다. 순서는 [2. 입력 파일 준비](02-input.md)의 "견본 데이터로 먼저 시험하기"에 있습니다.

**파일을 넣었는데 표가 대응되지 않습니다.**
파일 이름에 표 이름이 없고 헤더도 명세 컬럼과 60% 미만으로 겹치면 자동 대응이 되지 않습니다. 대응표의 드롭다운에서 직접 고르거나, 파일 이름을 표 이름(예: `PERSON.csv`)으로 바꿉니다.

**엑셀 파일의 시트가 일부만 인식됩니다.**
시트 하나가 표 하나여야 합니다. 시트 이름에 표 이름을 넣으면 확실합니다. 첫 줄이 헤더가 아니거나 제목 행이 있으면 지웁니다.

**한글이 깨져 보입니다.**
파일이 EUC-KR인데 다른 인코딩으로 잘못 저장된 경우입니다. 병원 시스템에서 다시 내보내거나, 엑셀에서 열어 UTF-8 CSV로 저장합니다. 정상 EUC-KR 파일은 프로그램이 알아서 변환합니다. UTF-16("유니코드 텍스트")은 읽지 못하므로 UTF-8 로 저장합니다.

**컬럼 이름이 전부 대문자로 나옵니다.**
그대로 넣어도 됩니다. 소문자 명세 이름으로 맞춰 읽고 참고로 표시합니다.

**빈 칸에 `NULL` 이라고 적혀 나옵니다.**
그대로 넣어도 됩니다. `NULL`, `NA`, `N/A` 같은 글자는 빈 값으로 읽고, 몇 개였는지 보고서의 '입력 정규화'에 적습니다. 필수 항목이면 필수값 누락으로 보고됩니다. 단, **`LYMPHOMA.cell_of_origin` 열의 `NA`** 는 DLBCL 이 아닐 때 적는 값이라 그대로 값으로 읽습니다.

**"기본키 또는 person_id 누락" 오류로 실행이 막힙니다.**
헤더에 그 표의 기본키(예: `visit_occurrence_id`)와 `person_id` 컬럼이 있어야 합니다. 컬럼 이름의 철자를 명세와 맞춥니다. 컬럼 명세서는 **입력 양식 내려받기**에서 받을 수 있습니다.

**날짜가 `2026/03/15`처럼 되어 있습니다.**
`YYYY-MM-DD`로 바꿔야 합니다. 엑셀에서는 셀을 날짜 형식으로 두면 프로그램이 변환합니다. CSV에서는 내보낼 때 형식을 지정합니다. `2026-03-15 00:00:00` 처럼 시각만 붙은 것은 알아서 날짜로 읽습니다.

## 결과

**위반이 너무 많이 나옵니다. 어디부터 봐야 하나요?**
**결과 보고서**에서 미검사·실행 오류를 먼저 확인한 뒤 **우선 확인할 위반 규칙**을 봅니다. 오류 우선·같은 심각도에서는 위반 수 내림차순입니다. 규칙 이름을 누르면 해당 위반 행으로 이동합니다. 컬럼 구성·타입 문제 하나가 수천 건을 만들 수 있으니 원인을 고친 뒤 재검증하세요.

**위반율이 2.4% 라는 것은 환자의 2.4% 가 틀렸다는 뜻인가요?**
아닙니다. 전체 위반율은 **위반 건수 ÷ 입력 표 행 수의 합**이고, 위반 건수는 오류와 경고를 모두 합친 (규칙, 행) 쌍의 수입니다. 한 행이 여러 규칙을 어기면 중복으로 세므로 오류가 있는 환자나 행의 비율이 아닙니다. 규칙마다의 비율은 `rule_results.csv` 의 위반 수와 검사 행 수(`rows_checked`)로 따로 계산합니다([4장](04-output.md)의 "건수와 비율 읽기").

**위반이 0건이면 모든 규칙을 통과한 건가요?**
규칙 상태를 함께 봅니다. `skipped`(표가 없어 건너뜀), `error`(실행 오류), `disabled`(꺼짐) 규칙은 위반이 0 으로 기록되지만 **통과가 아니라 미확인**입니다. 통과는 `pass` 뿐입니다.

**이전의 "우수"·"양호"·"주의"·"위험" 표시가 없어졌나요?**
네. 중복 집계되는 비율을 품질 등급으로 오해하지 않도록 제거했습니다. 오류·경고 건수와 미검사·실행 오류 상태를 따로 표시합니다. 공식 접수·합격이나 임상 품질 인증을 뜻하지 않습니다.

**데이터 충실도 비율이 낮으면 데이터가 나쁜 건가요?**
아닙니다. 데이터 충실도는 규칙 위반이 아니라 "있어야 할 기록이 실제로 있는가"를 센 **비율**이며 합격·불합격이나 목표값이 없습니다. 기록이 없는 이유(검사를 하지 않음, 다른 시스템에 기록, 이 표에 적재하지 않음 등)는 프로그램이 알 수 없고 단정하지도 않습니다. 병기·바이오마커는 MEASUREMENT 행(LOINC 검사)으로 적재해야 셉니다. 미충족 목록(`sufficiency.csv`)은 환자 단위라 기관 내부에서만 쓰고 중앙에는 보내지 않습니다([4장](04-output.md)의 "데이터 충실도").

**보고서에 실제 입력값이나 SQL 오류 상세가 없습니다.**
외부용 파일에서는 입력 예시와 DB 오류 원문을 제외합니다. 실제 위반 값은 **위반 상세** 화면의 **상세 보기**나 내부용 `findings.csv`, SQL 오류 원문은 앱 내부 실행 기록에서 봅니다.

**미래 날짜 오류가 나오는데 실제로는 맞는 날짜입니다.**
검증 기준일로 판정합니다. **설정** 또는 실행 화면의 **검증 기준일**이 기관이 정한 날짜인지 확인하고 다시 실행합니다. 실제 실행 시각과는 별개입니다.

**규칙이 잘못됐다고 생각됩니다.**
그럴 수 있습니다. 규칙은 가상데이터로만 검증했고 실제 병원 데이터는 처음입니다. 우리 기관의 사정 때문에 어떤 규칙이 맞지 않는다면 규칙을 끄거나 범위를 조정해 실행할 수 있고([6. 규칙 편집](06-rules.md)), 규칙 id 와 왜 그렇게 생각하는지를 파일럿 피드백 양식에 적어 보내 주세요. **환자 ID, 날짜, 값 같은 실제 환자 정보는 적지 않습니다.** 위반 행의 값도, 값이 보이는 화면 캡처도 보내지 않습니다(작성 요령은 [파일럿 피드백 양식](../pilot/feedback.md)).

**어떤 파일을 중앙에 보내나요?**
파일럿에서는 `submission.json` 하나입니다. **제출용 집계 저장**으로 저장한 뒤 기관이 열어 `label` 등에 식별 정보가 없는지 확인하고, 내용은 고치지 않습니다. 내부용 전체 묶음·위반 CSV·`sufficiency.csv` 는 보내지 않습니다. `report.md`·`rule_results.csv`·`summary.json`도 기관이 확인하고 중앙이 요청한 경우에만 공유합니다. 앱은 자동 전송하지 않습니다.

**`submission.json` 의 해시가 있으면 파일이 위조되지 않았다는 증명이 되나요?**
아닙니다. 해시는 실행에 쓴 규칙 묶음의 지문이며 파일의 진본성을 증명하지 않습니다. 서명이 없는 일반 텍스트 파일이라 고치면 알 수 없습니다([4장](04-output.md)의 "해시와 진본성").

**규칙 내용을 미리 볼 수 있나요?**
**검증 규칙 관리** 화면에서 규칙을 검색해 설명, 검사 대상, 교차 규칙의 SQL, 조치 안내를 볼 수 있습니다.

## 관리자 모드

**관리자 모드는 비밀번호로 보호되나요? 변경 기록은 믿을 수 있나요?**
아닙니다. **설정**의 단추를 누르면 누구든 켤 수 있고 비밀번호나 인증이 없습니다. 변경 이력(`rule-history.jsonl`)은 이 PC 의 일반 텍스트 파일이라 고치거나 지울 수 있고, 누가 바꿨는지나 누가 승인했는지는 기록하지 않습니다. 누가 SQL 을 바꿀 수 있는지, 승인이 필요한지는 **기관 정책**으로 정해야 합니다. 자세한 내용은 [6장](06-rules.md)입니다.
