# 4. 출력물 읽기와 제출

## 출력 파일과 공유 분류

실행마다 기본 출력 7종과 실행 당시 기준 보관 파일 2종이 생깁니다. 이 프로그램은 파일을 어디에도 자동으로 보내지 않습니다. 아래 분류는 **파일 안에 무엇이 들어 있는가**에 따른 것이며, 기관 밖 반출의 최종 판단은 **기관의 정보보안·반출 정책**에 따릅니다.

| 파일 | 내용 | 분류 |
|---|---|---|
| `findings.csv` | 위반 행 목록. 규칙, 테이블, 행 키, 환자 ID, 상세. 병원 안에서 데이터를 고칠 때 씁니다 | **기관 내부 전용.** 환자 단위 정보. 외부 제출 금지 |
| `sufficiency.csv` | 데이터 충실도 미충족 환자·요법과 사유. 환자 단위 | **기관 내부 전용.** 환자 단위 정보. 외부 제출 금지 |
| `report.md` | 검증 보고서. 요약, 분류별 집계, 실패 규칙별 건수, 입력 정규화. 규칙 설정을 바꿔 실행했다면 `## 규칙 설정` 절. 입력 원문 예시와 DB 오류 원문은 넣지 않습니다 | 집계와 규칙 정보만 담음. **기관이 내용을 확인한 뒤** 공유 |
| `report.pdf` | `report.md`와 같은 내용을 A4 PDF로 만든 것(쪽 번호 포함). 앱이 실행 끝에 만들며, 이전 실행은 출력 목록을 열 때·결과 보고서의 **PDF 저장**·기관 내부용 묶음 내보내기 때 생성합니다. Python·TypeScript CLI 엔진은 만들지 않습니다. 환자 단위 정보는 없습니다 | 집계와 규칙 정보만 담음. **기관이 내용을 확인한 뒤** 공유 |
| `rule_results.csv` | 코호트에 적용된 규칙 전체의 상태(통과·실패·건너뜀·오류·꺼짐), 위반 수, 규칙이 검사한 행 수, 규칙 출처(`origin`: 표준·변경·사용자·관리자) | 집계와 규칙 정보만 담음. **기관이 내용을 확인한 뒤** 공유 |
| `summary.json` | 규칙 단위 요약. DB 오류 원문은 정해진 오류 안내로 대체합니다. 프로그램 간 비교용 | 집계와 규칙 정보만 담음. **기관이 내용을 확인한 뒤** 공유 |
| `submission.json` | 중앙 제출용 집계(`schema: kai-dq-submission/3`). 규칙별 상태와 건수, 테이블 행 수, 입력 정규화 건수, 데이터 충실도 집계(`sufficiency`), 실행 이름(`label`), 규칙 설정 요약(`rule_set`) | 파일럿에서 중앙에 보내는 파일. 환자·행 단위 정보는 넣지 않도록 만들었지만 **보내기 전에 기관이 직접 열어 확인**합니다 |
| `criteria.zip` | 실행 당시 기본 명세·규칙·코드표 전체 YAML과 패키지 메타데이터 | **기관 내부 전용.** 기관에서 받은 기준 내용이 포함될 수 있음 |
| `criteria-snapshot.json` | 실행 당시 실효 명세·규칙·기관 조정·SQL·기준일·해시·관리자 모드 | **기관 내부 전용.** 기관 규칙에 내부 정보가 포함될 수 있음 |

실행 폴더의 `input/`(정규화된 입력 사본), 앱 데이터 폴더의 `history.duckdb`, **위반 상세**에서 내보낸 CSV도 환자 단위 정보를 담은 **기관 내부 전용** 자료입니다.

"집계만 담음"은 이 프로그램이 환자 ID·행 키·입력 원문을 쓰지 않도록 만들어졌다는 뜻입니다. 실행 이름, 규칙 이름·설명·허용 코드·정규식처럼 **사용자가 직접 적은 글**과 작은 표의 행 수는 기관 상황에 따라 식별 정보가 될 수 있으므로 기관이 확인해야 합니다. 그 확인을 프로그램이 대신하지 않습니다.

## 데이터 충실도

DQ 규칙은 제출된 값이 명세와 논리에 맞는지 검사합니다. 데이터 충실도는 **분석에 필요한 기록이 제출 데이터에 있는지** 별도로 측정합니다. v1.0.11는 공통 5개와 질환별 36개, 총 41개를 정의하며, 선택한 코호트에 해당하는 항목만 보고합니다.

- **보고서(`report.md`)** 의 `## 데이터 충실도` 절: 항목, 단위, 대상 수, 충족 수, 비율, 1인·1년당 중앙값, 연령대(<50, 50-64, 65+, 미상)별 값.
- **앱 보고서 화면**의 '데이터 충실도' 카드: 같은 집계를 보여 줍니다.
- **`sufficiency.csv`**: 미충족 환자·요법과 사유 목록입니다. 환자 단위이므로 `findings.csv` 처럼 기관 안에서만 쓰고 밖으로 보내지 않습니다.
- **`submission.json`** 의 `sufficiency` 에는 집계만 들어갑니다.

**대상 수부터 확인하세요.** 항목마다 환자 또는 항암요법이 분모입니다. 예를 들어 당뇨병 연간 UACR 지표는 관찰 기간이 1년 이상인 환자에게 적용합니다. 분모가 0이거나 표가 없어 계산을 건너뛴 경우는 충족률 0%와 다릅니다. 비율은 합격 기준이나 목표값이 아닙니다.

**낮은 비율의 원인은 내부 CSV에서 확인하세요.** 첫 항암 전 EGFR·ALK 지표는 결과 코드·수치 또는 결과 원문이 있는 검사 행을 검사일로 평가합니다. 검사일은 실제 결과 보고일이 아닙니다. 별도의 구조화 결과 지표에서는 원문만 있으면 충족되지 않습니다. FIB-4는 구성 검사 누락, 같은 날 조합 없음, 수치·단위 문제, 나이 문제 등을 구분합니다.

제출 데이터에 기록이 없다고 해서 실제로 검사를 하지 않았다고 단정할 수 없습니다. 적재 누락이나 미매핑도 확인하세요. 첫 항암 전 EGFR·ALK 산식은 v1.0.8에서 바뀌었으므로, v1.0.7과 동일 지표로 합산하지 마세요. [41개 항목별 기준과 한계](../docs/data-sufficiency.md)

## 표준 용어 매핑률

표준 개념 필드(`*_concept_id`, 원천 개념 필드 제외)마다 값이 `0`(매핑 실패 표시)인 행의 비율을 **미매핑률**로 보여 줍니다. 제출한 컬럼만 세고, 빈 값과 정수가 아닌 값은 대상에서 뺍니다. 규칙 위반 건수와는 별개의 참고 지표이며 합격·불합격 판정이 없습니다. `report.md`, 앱 보고서 화면, `submission.json` 에 필드별 집계만 실리고 환자 단위 값은 없습니다. `0` 이 맞는 경우(예: 표준 개념이 없는 항암 요법)도 미매핑에 들어가므로 해석할 때 구분하세요.

## 제출 규칙

- 파일럿에서 중앙에 보내는 파일은 `submission.json` 하나입니다. 환자나 행 단위 정보는 넣지 않게 만들었습니다. 그래도 **보내기 전에 텍스트 편집기로 열어** 다음을 확인합니다.
  - `label`(실행 이름)에 환자·병원 내부 식별 정보가 없는가
  - `rule_set` 의 변경 내용, 사용자 규칙 id 에 식별 정보가 없는가
  - `cohort`, `run_date`, `run_id` 가 보내려는 실행이 맞는가
  - 이 실행을 **표준 규칙 상태**로 한 것인지, 규칙을 조정한 것인지(`rule_set`)
- 파일의 내용은 **고치지 않고** 그대로 보냅니다. 내용을 고친 파일은 중앙이 알아볼 방법이 없습니다([진본성](#해시와-진본성) 참조).
- `findings.csv`, `sufficiency.csv` 는 환자 ID와 값이 들어 있으므로 병원 밖으로 내보내지 않습니다. 데이터 담당자가 원천 데이터를 고치거나 기록을 보완할 때만 씁니다.
- **기관 내부용 전체 묶음 저장**으로 만든 폴더에도 `findings.csv`, `sufficiency.csv`가 들어 있습니다. 폴더째 보내지 말고 **제출용 집계 저장**으로 `submission.json`만 저장해 검토한 뒤 제출합니다.
- 실행 이름(`label`)은 `submission.json` 에 그대로 실립니다. 환자를 알아볼 수 있는 말을 넣지 않습니다.
- 규칙 이름·설명·허용 코드·정규식 등 규칙 설정에도 환자 정보를 넣지 않습니다. 설정 메타데이터는 결과물에 기록될 수 있습니다.
- 규칙 설정을 바꿨다면 `submission.json` 에 그 사실(`rule_set`)이 실립니다. 중앙은 표준 규칙만으로 실행한 결과와 따로 집계하므로 숨기지 말고 그대로 보냅니다. → [6. 규칙 편집](06-rules.md)
- 전달 방법(채널)과 파일 이름 규칙은 이 프로그램이 정하지 않습니다. 중앙이 안내하는 방법과 기관의 반출 정책을 따릅니다.

### 파일 이름

| 만드는 방법 | 파일 이름과 위치 |
|---|---|
| 실행 폴더에서 직접 | `runs/<실행 ID>/submission.json` |
| **제출용 집계 저장** | 기본 이름이 `<실행 ID>_submission.json` (저장할 때 바꿀 수 있음) |
| **기관 내부용 전체 묶음 저장** | 선택한 폴더 아래 `<실행 ID>/submission.json` (다른 내부 파일도 함께 포함) |

실행 ID 는 `<코호트>_<날짜>_<시각>` 형식입니다(예: `LUNG_CANCER_20261116_123456789`, 시각은 UTC). 두 번 이상 보낼 때는 실행 ID 로 구분됩니다. 중앙의 집계 도구는 파일 이름과 폴더 위치에 따라 읽는 방식이 달라지므로([파일럿 키트](../pilot/README.md)), **파일 이름을 임의로 바꿨다면 중앙에 알려 줍니다.**

### 해시와 진본성

`submission.json` 의 `rule_set.standard_hash`, `rule_set.effective_hash` 는 **어떤 규칙 묶음으로 실행했는지**를 가리키는 지문입니다. 그 파일을 누가 만들었는지, 보낸 뒤 내용이 바뀌지 않았는지(진본성·무결성)를 증명하지 않습니다. `submission.json` 에는 서명이 없고 일반 텍스트 파일이므로 누구든 고칠 수 있습니다. 설치 파일의 `SHA256SUMS.txt` 도 설치 파일 대조용이며 결과 파일과는 관계가 없습니다. 보낸 사람 확인과 접수 기록은 중앙 운영 절차와 기관 담당자의 책임으로 다룹니다.

## 건수와 비율 읽기

화면과 파일의 숫자는 아래 정의를 따릅니다([3장](03-run.md)의 표도 같습니다).

| 숫자 | 정의 | 읽는 법 |
|---|---|---|
| 입력 행 수 | 넣은 표들의 행 수 합계 | 전체 위반율의 분모. 환자 수가 아님 |
| 위반 건수 | (규칙, 행) 쌍의 수. **오류와 경고를 모두** 포함 | 오류만이 아님. 오류·경고 내역은 따로 표시 |
| 전체 위반율 | 위반 건수 ÷ 입력 행 수 | 한 행이 여러 규칙을 어기면 중복으로 센다. **오류가 있는 환자·행의 비율이 아니며**, 100% 를 넘을 수 있다 |
| 규칙별 위반율 | 그 규칙의 위반 수 ÷ 그 규칙이 검사한 행 수(`rows_checked`) | `rule_results.csv` 와 `submission.json` 의 `by_rule` 값으로 계산. 규칙마다 분모가 다르다 |

예: 입력 표 행이 모두 50,000 이고 위반이 1,200 건이면 전체 위반율은 2.4% 입니다. 그러나 이것이 "50,000 행 중 1,200 행이 틀렸다"는 뜻은 아닙니다. 한 행이 규칙 3개를 어겼다면 3건으로 셉니다. 한 규칙이 환자 1,000 행을 검사해 30 건을 잡았다면 그 규칙의 위반율은 3.0% 입니다.

전체 위반율은 규칙의 개수와 구성, 코호트의 표 개수, 큰 표(MEASUREMENT 등)의 행 수에 크게 좌우됩니다. 기관 간·코호트 간 단순 비교에는 쓰지 말고, 규칙별 결과를 봅니다.

### 규칙 상태: 통과가 아닌 것

`rule_results.csv` 의 `status`, `submission.json` 의 `by_rule[].status` 는 다섯 값입니다.

| 상태 | 뜻 | 통과인가 |
|---|---|---|
| `pass` | 규칙을 실행했고 위반 0건 | 예 |
| `fail` | 규칙을 실행했고 위반이 있음 | 아니오 |
| `skipped` | 필요한 표가 없어 실행하지 못함 | **아니오** (검사하지 않음) |
| `error` | 규칙 실행 중 오류가 남 | **아니오** (검사하지 못함. 상세는 앱 내부 실행 기록) |
| `disabled` | 사용자가 규칙을 껐음 | **아니오** (검사하지 않음) |

`skipped`·`error`·`disabled` 규칙의 위반 건수는 0 으로 기록되지만 "위반이 없음을 확인했다"는 뜻이 아닙니다. 그 규칙이 다루는 항목은 **미확인**입니다. 위반 0건을 보고하기 전에 이 세 가지의 수를 먼저 봅니다. `submission.json` 의 `rules.total` 에는 꺼진 규칙이 포함되어 있고 `rules.skipped`·`rules.error`·`rules.disabled` 가 따로 있습니다.

## 보고서 읽기

`report.md`와 **결과 보고서** 화면은 대부분 같은 내용을 보여 줍니다.

1. **요약**: 검증 기준일, 테이블 수, 규칙 수와 위반 건수. 화면은 오류·경고·실행 오류·미검사를 분리하고, 검사 불완전 사유를 먼저 표시합니다. 입력 행 대비 위반 건수 계산은 **분류별 통계 · 입력 행 수 · 계산 지표**를 펼쳐 보조로 확인합니다. `report.md`의 규칙 상태 값과 파일 형식은 바꾸지 않았습니다.
2. **규칙 설정** (규칙 설정을 바꿔 실행했거나 관리자 모드를 쓴 경우에만): 표준 규칙 묶음 해시와 실제로 쓴 규칙 묶음 해시, 관리자 모드 사용 여부, 표준과 달라진 규칙의 표(규칙 id · 출처 · 변경 내용). 규칙 설정이지 환자 데이터가 아닙니다. 설정을 바꾸지 않았다면 이 절이 없습니다.
3. **분류별 집계**: 적합성(형식·코드·관계), 완전성(필수값), 타당성(범위·논리) 세 축의 위반 수.
4. **테이블 행 수**: 넣은 표별 행 수. 합쳐 읽은 표는 합친 뒤의 수입니다.
5. **위반 발견 규칙별 건수**: 화면에서는 오류 우선·같은 심각도에서는 위반 수 내림차순으로 표시합니다. 규칙 이름을 누르면 해당 실행·규칙의 **위반 상세**로 이동합니다. 실제 값은 이 화면이나 내부용 `findings.csv`에서 확인합니다. SQL 실행 오류 원문은 외부용 보고서·집계가 아니라 앱 내부 실행 기록에서 확인합니다.
6. **입력 정규화**: 검증 전에 걷어 낸 내보내기 흔적(`NULL` 글자, `.0`, `00:00:00`, 대소문자 컬럼명, 빈 끝 컬럼, 양끝 공백)의 표별 건수. 손댄 것이 없으면 이 절이 없습니다.

## 심각도와 조치

| 심각도 | 뜻 | 조치 |
|---|---|---|
| 오류 (error) | **매뉴얼에 적힌 것**의 위반: 표·컬럼 구성, 필수, 타입, PK/FK, 코드표, 매뉴얼이 정한 조건부 규칙(예: 매일 투여면 `days_supply` 필수) | 데이터 보완 또는 수정. 수정 후 제출 |
| 경고 (warning) | 매뉴얼 밖의 제약·임상 개연성: 임상 상식 범위, OMOP 대표 코드 집합, 명세에 없는 추가 컬럼, 병기군 표기(`LD`/`ED` 등), 항종양제의 `sact_id` 연결 확인 | 검토 후 맞으면 그대로 둠. 병원 코드나 관행 때문이면 파일럿 피드백으로 알림 |

### 상태는 비율 등급이 아닙니다

우수·양호·주의·위험처럼 전체 위반율로 매기던 표시를 제거했습니다. 대신 오류 수정 필요, 경고 검토 필요, 검사 범위 확인 필요, 실행 오류, 보고된 위반 없음으로 구분합니다. **보고된 위반 없음도 임상 품질 인증이나 제출 승인이라는 뜻이 아닙니다.** 접수·수정 요구는 중앙의 안내와 기관 정책을 따릅니다.

## 검사 유형별 조치 안내

**위반 상세** 화면과 **검증 규칙 관리** 화면의 규칙 상세에서 같은 안내를 볼 수 있습니다.

| 검사 유형 | 뜻 | 조치 |
|---|---|---|
| 테이블 누락 | 필요한 표 파일이 없음 | 코호트 구성에 맞는 파일을 모두 제출. 사례가 없으면 헤더만 있는 파일 |
| 컬럼 누락 | 매뉴얼의 컬럼이 파일에 없음 | 컬럼명을 명세에 맞춤. 컬럼 명세서 참고 |
| 명세 외 컬럼 (경고) | 매뉴얼에 없는 컬럼이 파일에 있음 | 검사에는 쓰이지 않음. 필요 없으면 뺌 |
| 키 중복·누락 | 기본키가 비었거나 중복 | 행 식별자를 고유하게 부여. 두 폴더를 합쳐 읽을 때 같은 행이 두 번 있는지 확인 |
| 필수값 누락 | 필수 항목이 비어 있음 | 원천 시스템에서 값을 보완 |
| 데이터 타입 불일치 | 값의 형식이 명세와 다름 | 날짜는 YYYY-MM-DD, 숫자는 숫자만 |
| 코드표 밖 값 | 코드 컬럼이 매뉴얼의 코드 목록에 없음 (OMOP 대표 코드 집합이면 경고) | `1`·`0`·`9` 처럼 목록의 코드를 그대로. 병원 코드가 맞다면 경고는 규칙 설정에서 허용 코드를 추가 |
| 범위 밖 값 (경고) | 임상 상식 범위를 벗어남 | 입력 오류인지 확인. 실제 값이 맞으면 규칙 설정에서 범위를 조정 |
| 관계 무결성 오류 | 참조하는 행이 없음 (예: DRUG_EXPOSURE 의 `sact_id` 가 SACT 에 없음) | 참조 표의 누락 행을 함께 제출 |
| 비항암 코호트의 `sact_id` | SACT 가 없는 코호트(대사이상지방간·당뇨병)에서 `sact_id` 를 적음 | 비워 둠 |
| 미래 날짜 | 검증 기준일 이후 날짜 | 입력 오류인지 확인. 기관이 정한 검증 기준일로 맞춤 |
| 논리·교차 검증 | 표 간 논리 불일치 (사망 뒤 사건, 방문 기간 밖 사건, 약물 종료일과 `days_supply` 등) | 상세 내용의 날짜·값 관계를 확인 |

## 위반 행 찾기

**위반 상세**에서 실행을 고르고 규칙·테이블·심각도·검색어로 걸러 봅니다. 행의 **상세 보기**를 누르면 상세 전문, 테이블·필드, 행 키·환자 ID, 기대 조건과 확인 방법을 보여 줍니다. 기대 조건은 **실행 당시 보관한 규칙**을 사용합니다. 원본이 보관되지 않은 이전 실행은 그 사실을 알리며 현재 규칙으로 대신 설명하지 않습니다. Escape로 닫고 원래 버튼으로 돌아갑니다. 원천 데이터는 직접 수정합니다.

- **현재 조건 CSV 저장**: 현재 조회 조건에 맞는 **모든 쪽**의 행을 저장합니다. 화면 한 쪽(100행)만 저장하는 것이 아닙니다.
- **전체 위반 CSV 저장**: 필터와 관계없이 선택한 실행의 전체 위반을 저장합니다.
- 두 버튼의 CSV는 UTF-8 BOM 형식이며, Excel에서 수식으로 해석할 수 있는 시작 문자는 작은따옴표를 붙여 글자로 저장합니다. 실행 폴더의 원본 `findings.csv`나 전체 결과 묶음은 그대로이므로 이 변환이 적용되지 않습니다.
- 저장 성공·취소·실패를 화면에 알립니다. 두 CSV 모두 환자 단위 정보를 포함하므로 기관 내부에만 보관하세요.
